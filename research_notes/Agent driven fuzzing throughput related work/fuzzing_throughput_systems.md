## Key Question 1: What techniques reduce per-execution overhead? (persistent mode, fork servers, snapshots, coverage-guided tracing, instrumentation reduction, binary rewriting, LibAFL, Intel PT)

### Takeaway

The field attacks per-execution overhead along five distinct axes — (a) **eliminating process setup** (fork server → persistent mode → snapshot restore), (b) **eliminating coverage tracing** (coverage-guided tracing, self-modifying tracing, hardware tracing), (c) **reducing instrumentation density** (CFG-based pruning, sanitizer debloating, decoupled sanitization), (d) **better binary rewriting** so binary-only fuzzing approaches compiler-level speed, and (e) **removing OS/syscall cost** (user-space VFS, new OS primitives, scalable fork). Every one of these modifies the *fuzzer, the compiler pass, the rewriter, the OS, or the hypervisor* — none of them rewrites the target's own algorithms or caches input-invariant work at the source level.

### Cited Findings

#### RECENT (2024–2026)

- **ClosureX: Compiler Support for Correct Persistent Fuzzing** — published in the *Proceedings of the 30th ACM International Conference on Architectural Support for Programming Languages and Operating Systems (ASPLOS 2025), Volume 1*, DOI 10.1145/3669940.3707281. Mechanism: five LLVM passes (RenameMainPass, GlobalPass, HeapPass, FilePass, ExitPass) that track and undo only *test-case-execution-specific* state — globals byte-snapshotted into a dedicated `closure_global_section`, heap allocations tracked in a hash map, file descriptors hooked, stack restored via setjmp/longjmp — so persistent mode becomes semantically correct. "Users need make no additional modifications to the source code or be aware of persistent mode fuzzing at all." — [ACM DL listing via search](https://dl.acm.org/doi/10.1145/3669940.3707281); mechanism detail from the companion Virginia Tech MS thesis, *CLOSUREX: Transforming Source Code for Correct Persistent Fuzzing*, Rishi Ranjan, Virginia Polytechnic Institute and State University, 2024 — [VT thesis PDF](https://vtechworks.lib.vt.edu/bitstreams/820014dd-aaae-4bc6-8c4f-0f739a5fd78c/download). **UNVERIFIED:** the full ASPLOS author list (ACM DL returns a bot-check page; only Rishi Ranjan is verified, as thesis author, with Matthew D. Hicks as advisor).
- **Towards Correct and Efficient Persistent Fuzzing: Reducing Instrumentation Overhead and Managing Program State** — Sydney K. Earp, MS thesis, Virginia Polytechnic Institute and State University, 2025. Two mechanisms: (i) **dynamic instrumentation removal** — once an edge is discovered, the corresponding `trace_pc_guard` call site is patched to NOPs at runtime, "preserving binary layout and control flow"; (ii) **state-managed persistent mode** via three LLVM passes (GlobalPass, DynamicPass wrapping malloc/free, CleanupPass hooking file I/O and exit), achieving persistent execution "without requiring OS-level support or recompilation." — [VT thesis PDF](https://vtechworks.lib.vt.edu/server/api/core/bitstreams/0001a39d-7a3b-49f0-8e4e-8f50adcc0282/content)
- **SAND: Decoupling Sanitization from Fuzzing for Low Overhead** — ICSE 2025 (IEEE/ACM International Conference on Software Engineering); arXiv:2402.16497. Mechanism: fuzz the *normally built* (unsanitized) program and only re-run inputs on sanitizer-enabled builds when an "execution pattern" marks them interesting. Built on AFL++, evaluated on 20 real-world programs. — [arXiv abstract](https://arxiv.org/abs/2402.16497); [IEEE Xplore](https://ieeexplore.ieee.org/document/11029723/)
- **PeAR: A Static Binary Rewriting Framework for Binary-Only Fuzzing** — Alvin Charles, Adrian Herrera, Peter Oslington, Alwen Tiu; arXiv:2606.02126v1, 2 June 2026 (**preprint, no peer-reviewed venue confirmed**). Mechanism: reassembleable disassembly via Ddisasm + GTIRB; injects edge coverage through basic-block trampolines and adds forkserver init, deferred initialization, persistent mode, and shared-memory test-case delivery to stripped binaries. — [arXiv PDF](https://arxiv.org/pdf/2606.02126)
- **Pogofuzz: Profile-Guided Optimization for Fuzzing (Registered Report)** — Tobias Holl, Leon Weiß, Kevin Borgolte (Ruhr University Bochum); 5th International Fuzzing Workshop (FUZZING) 2026, co-located with NDSS, San Diego, 27 February 2026; DOI 10.14722/fuzzing.2026.23029. See Key Question 3 — this is the closest prior art to the user's project. — [NDSS FUZZING 2026 program](https://www.ndss-symposium.org/ndss-program/fuzzing-2026/); [paper PDF](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf); [authors' page](https://softsec.rub.de/publications/fuzzing2026-pogofuzz/)
- **E-FuzzEdge: Efficient In-Place Firmware Fuzzing via Parallel Scheduling** — Davide Rusconi, Osama Yousef, Mirco Picca, Danilo Bruschi (University of Milan), Flavio Toffalini (Ruhr-Universität Bochum), Andrea Lanzi (University of Milan); FUZZING 2026 @ NDSS. Explicitly framed as "improving the throughput of fuzzing campaigns in contexts where scalability is unavailable"; mechanism is parallel scheduling across multiple on-device processors. — [NDSS FUZZING 2026 program](https://www.ndss-symposium.org/ndss-program/fuzzing-2026/); [paper PDF](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-4.pdf)
- **EmbedFuzz: High Speed Fuzzing Through Transplantation** — arXiv:2412.12746 (December 2024). Mechanism: "firmware transplantation" converts binary MCU firmware into a functionally equivalent, fuzzing-enhanced binary that runs **natively** on a compatible high-end device instead of under emulation. — [arXiv PDF](https://arxiv.org/pdf/2412.12746); [author copy](https://nebelwelt.net/files/24arXiv.pdf). **UNVERIFIED:** peer-reviewed venue (the search result asserting NDSS 2025 was not corroborated by a primary source).
- **Tech-ASan: Two-stage check for Address Sanitizer** — arXiv:2506.05022 (2025); continues the sanitizer-overhead-reduction line. — [arXiv PDF](https://arxiv.org/pdf/2506.05022). **UNVERIFIED:** venue.
- **GPU / hardware offload (technique transfers only partially to C/C++ native fuzzing):** *Towards Smart Contract Fuzzing on GPUs*, IEEE S&P 2024 — converts the fuzzing workload into a SIMD task so thousands of GPU cores test simultaneously, motivated explicitly by "low throughput due to slow EVM execution ... #### SEMINAL (2017–2023)

**(a) Eliminating process setup**

- **Designing New Operating Primitives to Improve Fuzzing Performance** — Wen Xu, Sanidhya Kashyap, Changwoo Min, Taesoo Kim; CCS 2017, DOI 10.1145/3133956.3134046. Identifies that AFL "slows down by 24× because of file system contention and the scalability of fork() ... when it runs on 120 cores in parallel," and introduces three new OS primitives (snapshot syscall, dual file system service, shared in-memory log) to fix it. — [ACM DL](https://dl.acm.org/doi/10.1145/3133956.3134046); [author PDF](https://taesoo.kim/pubs/2017/xu:os-fuzz.pdf)
- **Agamotto: Accelerating Kernel Driver Fuzzing with Lightweight Virtual Machine Checkpoints** — Dokyung Song, Felicitas Hetzelt, Jonghwan Kim, Brent ByungHoon Kang, Jean-Pierre Seifert, Michael Franz; 29th USENIX Security Symposium, 2020. Mechanism: dynamically create *multiple* VM checkpoints while executing a syscall sequence and skip prefixes of subsequent test cases. Known limitation: "after one gigabyte is used to store snapshots, Agamotto begins to discard old snapshots causing it to slow down." — [USENIX page](https://www.usenix.org/conference/usenixsecurity20/presentation/song); [PDF](https://www.usenix.org/system/files/sec20-song.pdf)
- **Nyx: Greybox Hypervisor Fuzzing using Fast Snapshots and Affine Types** — Sergej Schumilo, Cornelius Aschermann, Ali Abbasi, Simon Wörner, Thorsten Holz; 30th USENIX Security Symposium, August 2021. Full-VM snapshot fuzzer built on modified KVM + QEMU with an in-kernel dirty-memory tracker and Intel-PT tracing for vCPUs; reloads the system under test "thousands of times per second." — [USENIX page](https://www.usenix.org/conference/usenixsecurity21/presentation/schumilo); [PDF](https://www.usenix.org/system/files/sec21-schumilo.pdf)
- **Nyx-Net: Network Fuzzing with Incremental Snapshots** — EuroSys 2022, DOI 10.1145/3492321.3519591; arXiv:2111.03013. Adds *incremental* snapshots so that secondary snapshots are nearly free. Also demonstrated on Firefox's IPC interface, servers, clients, and games. — [ACM DL PDF](https://dl.acm.org/doi/pdf/10.1145/3492321.3519591); [arXiv](https://arxiv.org/abs/2111.03013)
- **SnapFuzz: An Efficient Fuzzing Framework for Network Applications / SnapFuzz: high-throughput fuzzing of network applications** — Anastasios Andronidis, Cristian Cadar (Imperial College London); ISSTA 2022 (arXiv:2201.04048). Five mechanisms: a synchronous network fuzzing protocol replacing sleep-based delays; an in-memory filesystem via `memfd_create()` + Libsqlfs; a **smart deferred forkserver** that automatically places the snapshot at the latest safe point via binary rewriting (no manual `__AFL_INIT()` placement); UNIX domain sockets replacing TCP/IP; and suppression of stdout/stderr writes. — [arXiv PDF](https://arxiv.org/pdf/2201.04048). **UNVERIFIED:** the ISSTA 2022 venue string (the arXiv v2 is dated Jan 2023 and the ACM version title differs slightly); the ResearchGate record gives "SnapFuzz: high-throughput fuzzing of network applications."
- **Snappy: Efficient Fuzzing with Adaptive and Mutable Snapshots** — Elia Geretto et al. (VUSec); *Proceedings of the 38th Annual Computer Security Applications Conference (ACSAC 2022)*, DOI 10.1145/3564625.3564639. — [ACM DL](https://dl.acm.org/doi/10.1145/3564625.3564639); [VUSec PDF](https://download.vusec.net/papers/snappy_acsac22.pdf)
- **No Linux, No Problem: Fast and Correct Windows Binary Fuzzing via Target-embedded Snapshotting** — Stone et al.; 32nd USENIX Security Symposium, 2023. Motivating premise stated plainly: "high test case throughput enables more expeditious exploration," and existing high-performance fuzzers "exploit the Linux kernel's customizability to implement process snapshotting." — [USENIX page](https://www.usenix.org/conference/usenixsecurity23/presentation/stone); [PDF](https://www.usenix.org/system/files/usenixsecurity23-stone.pdf)
- **Forming Faster Firmware Fuzzers (SAFIREFUZZ)** — Lukas Seidel, Dominik Maier, Marius Muench; 32nd USENIX Security Symposium, Anaheim, 9 August 2023. High-level emulation + dynamic binary rewriting to run ARM Cortex-M firmware natively on far more powerful hardware. — [USENIX page](https://www.usenix.org/conference/usenixsecurity23/presentation/seidel); [PDF](https://www.usenix.org/system/files/usenixsecurity23-seidel.pdf)
- **AFL++ persistent mode / deferred fork server / shared memory test cases** — AFL++ official documentation. The docs state flatly: "Use persistent mode (x2-x20 speed increase)." They also recommend `AFL_TMPDIR` on tmpfs, `afl-persistent-config` kernel tuning, shared-memory test cases for libFuzzer-style harnesses, and ext2 with `noatime`. — [AFL++ "Fuzzing in Depth"](https://aflplus.plus/docs/fuzzing_in_depth/)

**(b) Eliminating coverage tracing**

- **Full-speed Fuzzing: Reducing Fuzzing Overhead through Coverage-guided Tracing** — Stefan Nagy, Matthew Hicks; 40th IEEE Symposium on Security and Privacy (S&P), May 2019; arXiv:1812.11875. Core insight: only a minuscule fraction of test cases increase coverage, so encode the coverage frontier *in the binary* (interrupt at the entry of not-yet-covered blocks) so the target self-reports new coverage and runs untraced otherwise. Implementation **UnTracer** uses Dyninst static binary instrumentation. — [arXiv](https://arxiv.org/abs/1812.11875); [S&P PDF mirror](https://wcventure.github.io/FuzzingPaper/Paper/SP19_Full-speed.pdf); [code](https://github.com/FoRTE-Research/UnTracer-AFL)
- **Same Coverage, Less Bloat: Accelerating Binary-only Fuzzing with Coverage-preserving Coverage-guided Tracing (HeXcite)** — Stefan Nagy, Anh Nguyen-Tuong, Jason D. Hiser, Jack W. Davidson, Matthew Hicks; ACM CCS 2021; arXiv:2209.03441. Extends CGT — which only supports basic-block coverage — to **edge coverage and hit counts** via *jump mistargeting* (redirect conditional-jump targets to interrupt addresses) and *bucketed unrolling* (binarize hit-count buckets at loop headers). Built on AFL 2.52b + the ZAFL rewriter. — [arXiv](https://arxiv.org/abs/2209.03441); [code](https://github.com/FoRTE-Research/HeXcite)
- **Zeror: Speed Up Fuzzing with Coverage-sensitive Tracing and Scheduling** — Zhou, Wang et al.; 35th IEEE/ACM International Conference on Automated Software Engineering (ASE 2020), Melbourne, September 2020; DOI 10.1145/3324884.3416572. Two parts: a **self-modifying tracing** mechanism giving zero-overhead instrumentation, plus a real-time scheduler that adaptively switches between the zero-overhead binary and the fully instrumented binary so coverage accuracy is not permanently sacrificed. — [ACM DL](https://dl.acm.org/doi/10.1145/3324884.3416572); [IEEE Xplore](https://ieeexplore.ieee.org/document/9286017/); [author PDF](http://wingtecher.com/themes/WingTecherResearch/assets/papers/ase20.pdf)
- **Enhancing Coverage-Guided Fuzzing via Phantom Program (MirageFuzz)** — ESEC/FSE 2023, DOI 10.1145/3611643.3616294. Builds a "phantom" of the target that reduces program dependencies for conditional statements "while retaining their original semantics," so more program states are reachable per seed. — [ACM DL](https://dl.acm.org/doi/10.1145/3611643.3616294); [author PDF](https://zhangyuqun.github.io/publications/fse2023a.pdf). *Note: this is a semantics-retaining program transformation, but its goal is state exploration, not execs/sec; I found no execs/sec speedup number for it.*

**(c) Reducing instrumentation density / sanitizer cost**

- **INSTRIM: Lightweight Instrumentation for Coverage-guided Fuzzing** — Chin-Chia Hsu, Che-Yu Wu et al.; NDSS Workshop on Binary Analysis Research (BAR) 2018. Finds that ASan's >1× overhead "is mainly caused by the extensive sanitizer checks on memory accesses" and assembles a set of optimizations to remove redundant checks. — [USENIX page](https://www.usenix.org/conference/usenixsecurity22/presentation/zhang-yuchen); [PDF](https://www.usenix.org/system/files/sec22summer_zhang-yuchen.pdf)
- **StochFuzz: Sound and Cost-effective Fuzzing of Stripped Binaries by Incremental and Stochastic Rewriting** — Zhuo Zhang et al.; 42nd IEEE Symposium on Security and Privacy (S&P), 2021. Incremental/stochastic rewriting piggy-backs on the fuzzing run itself; many candidate rewritten binaries are generated and validated/invalidated by fuzzing runs. — [S&P proceedings PDF](https://conferences.computer.org/sp/pdfs/sp/2021/893400a659.pdf); [IEEE Xplore](https://ieeexplore.ieee.org/document/9519407/)

**(d) Better binary rewriting**

- **Breaking Through Binaries: Compiler-quality Instrumentation for Better Binary-only Fuzzing (ZAFL)** — Stefan Nagy, Anh Nguyen-Tuong, Jason D. Hiser, Jack W. Davidson, Matthew Hicks; 30th USENIX Security Symposium, 2021. Brings compiler-grade instrumentation and transformation passes to binary-only targets via the Zipr static rewriter. — [USENIX page](https://www.usenix.org/conference/usenixsecurity21/presentation/nagy); [PDF](https://www.usenix.org/system/files/sec21fall-nagy.pdf)

**(e) Hardware-assisted tracing**

- **kAFL: Hardware-Assisted Feedback Fuzzing for OS Kernels** — Schumilo et al.; 26th USENIX Security Symposium, 2017. Uses Intel Processor Trace for coverage; "because coverage measurement is performed using hardware tracing, the overhead is extremely low, reported to be less than 5%," and no instrumented rebuild is required. — [USENIX PDF](https://www.usenix.org/system/files/conference/usenixsecurity17/sec17-schumilo.pdf)
- **PTrix: Efficient Hardware-Assisted Fuzzing for COTS Binary** — Yaohui Chen, Dongliang Mu et al.; ACM AsiaCCS 2019, DOI 10.1145/3321705.3329828; arXiv:1905.10499. Key finding: naive Intel-PT fuzzing was *slower than QEMU-AFL* because decoding highly compressed PT traces is expensive; PTrix parallelizes PT-trace processing with target execution and feeds the *decoded trace itself* as feedback, avoiding coverage reconstruction. — [ACM DL](https://dl.acm.org/doi/10.1145/3321705.3329828); [arXiv](https://arxiv.org/abs/1905.10499); [PDF mirror](https://wcventure.github.io/FuzzingPaper/Paper/ASIACCS19_PTRIX.pdf)

**(f) Fuzzer-engine performance engineering**

- **LibAFL: A Framework to Build Modular and Reusable Fuzzers** — Andrea Fioraldi, Dominik Maier, Dongjia Zhang, Davide Balzarotti; *Proceedings of the 2022 ACM SIGSAC Conference on Computer and Communications Security (CCS 2022)*, Los Angeles, November 2022; DOI 10.1145/3548606.3560602. ### Inferences

- The overhead-reduction literature is organised around a strict taxonomy the user's work sits *outside* of: everyone else removes cost that the *fuzzing apparatus* adds (fork, trace, sanitize, emulate, syscall), whereas the user removes cost that the *target's own algorithm* incurs. That is a genuinely unoccupied axis and should be the framing.
- Persistent mode is the technique closest in spirit (it also needs a correctness argument about program state), and ClosureX / CCS'23 / Earp all spend most of their effort on *preserving semantics while going faster* — the same contract the user imposes. The difference: they preserve semantics by adding restore machinery around unchanged code; the user preserves semantics by changing the code and proving crash-equivalence.
- Coverage-guided tracing (UnTracer/HeXcite) is explicitly described by its own authors as "optimizing the target instead of the fuzzer" (Pogofuzz's related-work section makes this framing), so the user should expect reviewers to draw that comparison and should pre-empt it: CGT changes *instrumentation* in the target binary, not the target's computation.

### Gaps

- I could not find any peer-reviewed systematization specifically of *per-execution* overhead sources in C/C++ native fuzzing; the closest is the CCS 2023 profiling study (Key Question 5) and SoK: Prudent Evaluation Practices for Fuzzing (S&P 2024), which is about evaluation methodology rather than a throughput taxonomy.
- Exact author lists for ClosureX (ASPLOS 2025) and Snappy (ACSAC 2022) could not be confirmed against a primary source because ACM DL blocked automated access and dblp was unreachable.

## Key Question 2: What reported throughput multipliers does each claim, on what targets?

### Takeaway

Reported multipliers span four orders of magnitude, but they are **not comparable**: the huge numbers (300×–1062×) come from network/firmware/emulation settings with pathologically slow baselines, while general-purpose C/C++ user-space work lands in the **1.3×–4×** band, and the single piece of work that optimizes the target's *compiled code* rather than its execution harness (Pogofuzz) reports only **3.7% median / 29.7% max**.

### Inferences

- For positioning: the honest comparison band for a *general-purpose C/C++ user-space* throughput technique is **1.3×–4×** (UnTracer, ZAFL, ClosureX, PeAR, SAND, ASan--, CCS'23 state recovery). Anything the user reports in that band is competitive with the best published systems work.
- Pogofuzz's 3.7% median is the single most important comparison point: it shows that *compiler-level* optimization of the target, applied blindly, yields almost nothing and can regress (systemd, zlib). ## Key Question 3: Has anyone optimized the TARGET PROGRAM's own source or build (not the fuzzer) to go faster?

### Takeaway

**Yes, but only three ways, and none of them is what the user is doing.** (1) **Pogofuzz (FUZZING 2026)** applies compiler PGO to the target using fuzzer-derived profiles — same goal, but the optimization is chosen by the compiler, not by a semantic understanding of the code, and it yields only 3.7% median. (2) **ClosureX / CCS'23 / Earp** insert *compiler passes* into the target to make persistent mode correct — target-side, but adding restore machinery rather than making the computation cheaper. (3) **Practitioner guidance** (Chromium, google/fuzzing, AFL++) tells harness authors to hand-optimize, but with essentially no published data. **I found no peer-reviewed work that automatically edits a target's application source code to make it compute faster under a behavior-preservation contract.**

### Cited Findings

#### RECENT (2024–2026)

- **Pogofuzz explicitly claims the "optimize the target, not the fuzzer" niche.** Its stated insight is that "the inputs used for future mutations are known," so PGO can be aimed at exactly those inputs. Pipeline: (i) *Input Selection* — pick high-energy queue entries using the fuzzer's power schedule; (ii) *Profile Generation* — run them on an instrumented target, with a **custom LLVM pass that modifies IR-level PGO instrumentation to scale counter increments by test-case energy**; (iii) *Recompilation and Replacement* — on a timer (1 hour in the preliminary study), recompile with the new profile and swap the binary **in situ** without stopping other fuzzer processes. Self-described as "fuzzer-agnostic and target-agnostic," and "a significant departure from traditional fuzzer optimizations." Its related-work section states that prior work has "largely focused on improving or introducing fuzzer components" and that optimizing target programs for fuzzing "has only received little attention." — [paper PDF](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf); [authors' page](https://softsec.rub.de/publications/fuzzing2026-pogofuzz/)
- **Pogofuzz names post-link optimizers as the obvious next step but does NOT evaluate them:** it cites BOLT (Panchenko et al. 2019) and Propeller (Shen et al. 2023) as approaches that "can be adapted to further optimize the fuzzing target by adding a PLO (post-link optimization) step after recompilation," noting Propeller "improves on compiler-based PGO by 1.1%" in data-center deployments. It also cites AutoFDO (Chen et al. 2016) and CSSPGO-style context-sensitive PGO (He et al. 2024). — [paper PDF](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf)
- **Pogofuzz's cost model is a direct warning for the user's design:** single-core runs lost **up to 10% throughput** to recompilation, and two of four targets (systemd, zlib) regressed at 4 cores. The user's design — profile **once**, apply folds offline, keep only folds that improve replay time — structurally avoids both of these failure modes and is worth stating as an explicit advantage. — [paper PDF](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf)
- **ClosureX (ASPLOS 2025)** is target-side source/IR transformation, but its purpose is *correctness of persistent mode*, not making the target's own computation cheaper. Its own thesis version emphasizes that "users need make no additional modifications to the source code." It is explicitly described as "orthogonal to any such coverage collection mechanism," e.g. combinable with UnTracer. — [VT thesis PDF](https://vtechworks.lib.vt.edu/bitstreams/820014dd-aaae-4bc6-8c4f-0f739a5fd78c/download)
- **Earp (VT 2025)** likewise patches the target (NOPing out `trace_pc_guard` call sites at runtime; LLVM passes for state restore) — target-side, but again instrumentation/state machinery, not algorithmic. — [VT thesis PDF](https://vtechworks.lib.vt.edu/server/api/core/bitstreams/0001a39d-7a3b-49f0-8e4e-8f50adcc0282/content)
- **LLM-agent work in fuzzing is aimed at harness *construction*, not target speed.** HarnessAgent (arXiv:2512.03420) and OSS-Fuzz-Gen target automatic harness generation; OSS-Fuzz added "an agentic LLM-based approach for build script generation" in 2025. I found **no** LLM/agent work that edits target source for throughput. — [HarnessAgent](https://arxiv.org/html/2512.03420); [OSS-Fuzz LLM page](https://google.github.io/oss-fuzz/research/llms/target_generation/); [OSS-Fuzz blog on agentic build generation](https://blog.oss-fuzz.com/posts/oss-fuzz-integrations-via-agent-based-build-generation/)

#### SEMINAL (2017–2023) and practitioner guidance

- **Profile-Driven System Optimizations for Accelerated Greybox Fuzzing** — Yunhang Zhang, Chengbin Pang, Stefan Nagy, Xun Chen, Jun Xu; CCS 2023 (University of Utah, Nanjing University, Samsung Research America), DOI 10.1145/3576915.3616636. This is the closest *methodological* analogue to the user's approach: **profile the target for a short window (5 minutes), then patch the target based on that profile.** Two patches: (i) an LLVM pass (~900 LoC) + GCC plugin (~500 LoC) that identifies which global objects must be reset and inserts save/restore for exactly those, re-profiling only if stability drops below 95%; (ii) a **user-space virtual filesystem library (~1,400 LoC of C)** that intercepts POSIX file operations and keeps accessed files in memory. Profiling-and-patching cost: **4–61 seconds** per target; 9 of 20 benchmarks had identical global-object sets at 5 min and 24 h. — [ACM DL](https://dl.acm.org/doi/10.1145/3576915.3616636); [Utah PDF](https://futures.cs.utah.edu/papers/23CCS.pdf)
- **Chromium's "Efficient Fuzzing Guide"** is the canonical practitioner source and gives a hard threshold: "aim for at least 1,000 exec/s from your fuzz target locally before submitting it to the Chromium repository." Concrete target-side advice: avoid complex setup/teardown in `LLVMFuzzerTestOneInput`, "use static initialization and shared resources," de-allocate everything allocated inside the entry point, and "avoid allocation of dynamic memory wherever possible" because "memory instrumentation works faster for stack-based and static objects than for heap-allocated ones." It also advises testing "different variants for your fuzz target locally, then submit only the fastest implementation." **It provides no quantitative speedup data.** — [Chromium efficient_fuzzing.md](https://chromium.googlesource.com/chromium/src/+/main/testing/libfuzzer/efficient_fuzzing.md)
- **google/fuzzing "good-fuzz-target.md"** gives throughput norms and tells authors to profile: "a typical good fuzz target will have an order of 1000 executions per second per one CPU core on average or more, and for lightweight targets, 10000 exec/s or more, while if your fuzz target has less than 10 exec/s you are probably doing something wrong"; it recommends to "profile fuzz targets and eliminate any obvious hot spots." — [google/fuzzing docs](https://github.com/google/fuzzing/blob/master/docs/good-fuzz-target.md)
- **AFL++ build-flag guidance** recommends LTO mode (`afl-clang-lto`) as "the best possible" instrumentation, but notes LTO's long compile time as a counterweight; it gives no execs/sec numbers per instrumentation mode. — [AFL++ docs](https://aflplus.plus/docs/fuzzing_in_depth/); [README.lto.md](https://github.com/jtpereyda/AFLplusplus/blob/dev/instrumentation/README.lto.md)
- **rustc developer guide** is one of the few documents that explicitly proposes PGO/BOLT on a *fuzz target*: "For fuzzing a compiler, you may want to build it with `-C target-cpu=native` or even PGO/BOLT to squeeze out more executions per second. However, it's best to try multiple build configurations to see what actually results in superior throughput." — [Rust Compiler Development Guide](https://rustc-dev-guide.rust-lang.org/fuzzing.html)
- **Removing I/O from the harnessed path** is standard practitioner advice (tmpfs/ramdisk for corpus and `AFL_TMPDIR`), and SnapFuzz automated it (in-memory filesystem via `memfd_create()`, suppressing stdout/stderr writes, replacing TCP/IP with UNIX domain sockets, deleting developer-added sleeps). CCS'23's VFS library does the same at OS-abstraction level, removing **~87% of syscalls** and cutting kernel-space time by **42%**. — [SnapFuzz arXiv PDF](https://arxiv.org/pdf/2201.04048); [Utah CCS'23 PDF](https://futures.cs.utah.edu/papers/23CCS.pdf)

### Inferences

- The user's claim to novelty is defensible and narrow: **automated, hotspot-directed, semantics-preserving edits to the target's application source code (caching, memoization, algorithm/data-structure rewrites tuned to tiny inputs).** The three adjacent lines are (a) compiler-chosen optimization of the target (Pogofuzz), (b) compiler-inserted state machinery in the target (ClosureX/CCS'23/Earp), (c) hand-written harness hygiene (Chromium/google-fuzzing). None does (a')+(b')+(c') = *machine-chosen semantic rewrites of application logic*.
- Pogofuzz's weak result (3.7% median) is the strongest single argument for the user's thesis: if a compiler given perfect fuzzing-workload profiles can only buy ~4%, then the remaining headroom must be algorithmic, i.e. above the compiler's abstraction level — exactly where an LLM agent operates.
- CCS'23 already legitimizes "profile once, patch the target, keep it if stable" as a research methodology in a top-4 security venue. The user should cite it as methodological precedent while distinguishing on *what is patched* (state-reset code vs. the computation itself) and *how validity is checked* (fuzzing stability ≥95% vs. never-crash-less contract).
- Practitioner sources (Chromium, google/fuzzing) establish that this problem is **real and manually solved today at Google scale** — a strong motivation paragraph, since it means an automated agent is replacing human labor that is already being spent.

### Gaps

- I found **no** published measurement of what `-O3` vs `-O2`, `-march=native`, LTO, PGO or BOLT do to OSS-Fuzz target execs/sec as a controlled experiment (Pogofuzz is the only PGO data point and covers 4 targets). This is a genuine hole in the literature and the user could claim it.
- I found no work that quantifies how much of a typical OSS-Fuzz target's per-execution cost is input-invariant setup that could be hoisted or cached — which is precisely what the user's profiling would produce.
- The Pogofuzz reference `Zhang2023Optimization` in its bibliography could not be independently disambiguated beyond the CCS 2023 paper above; I treat them as the same work but flag it as an inference.

## Key Question 4: Does any prior work measure the END-TO-END effect of throughput gains on bug-finding time?

### Takeaway

Yes — several throughput papers report time-to-bug, and the gains are real but **strongly sublinear in throughput**. The governing empirical result is Böhme & Falk (ESEC/FSE 2020): exponentially more executions per minute buys only *linearly* more distinct bugs, though it does buy the *same* bugs proportionally faster. That second law is the one that justifies throughput work at all — and it is exactly the metric (time-to-bug on known bugs) the user is measuring with ARVO.

### Cited Findings

#### RECENT (2024–2026)

- **ClosureX (ASPLOS 2025 / VT thesis 2024)** measured time-to-bug directly: discovers bugs **1.9× faster** than AFL++ when both find the same vulnerability, and **25% more trials successfully discover bugs**. Example per-bug times: gpmf-parser division-by-zero 798 s (5/5 trials) vs. AFL++ 1386 s (5/5); c-blosc2 null-pointer 7148 s (4 trials) vs. 11896 s (2 trials); libbpf null-pointer 61 s (5/5) vs. 91 s (5/5). Also found **15 zero-day bugs across 4 programs, 4 CVEs, 7 patches deployed**. — [VT thesis PDF](https://vtechworks.lib.vt.edu/bitstreams/820014dd-aaae-4bc6-8c4f-0f739a5fd78c/download)
- **Large-Scale Empirical Analysis of Continuous Fuzzing: Insights from 1 Million Fuzzing Sessions** — Tatsuya Shirai, Olivier Nourry, Yutaro Kashiwa, Kenji Fujiwara, Yasutaka Kamei, Hajimu Iida; *IEEE Transactions on Software Engineering*, 2025 (arXiv:2510.16433). ~1.12 M fuzzing sessions, 878 OSS-Fuzz projects, March 2017–January 2025; >3.95 M build logs, 1.04 M coverage reports, 72,660 issue reports. Findings: **36% of projects detect a fuzzing bug during the first session and 20% during the second**; detection rates drop below 5% by the 26th session then plateau near a **2.19% median detection rate**; OSS-Fuzz runs "a fixed duration each day, typically around 10 minutes by default." **The paper does not quantify execs/sec.** It concludes bug detection relates to cumulative session frequency rather than individual execution speed. — [arXiv PDF](https://arxiv.org/pdf/2510.16433). **UNVERIFIED:** the exact TSE volume/issue string ("Vol. 14, No. 8, August 2025") returned by the fetch looks like a preprint template artifact and should not be reproduced verbatim.
- **SAND (ICSE 2025)**: "In 24 hours, compared to all the baseline fuzzers, SAND significantly discovers more bugs while not missing any" — i.e. removing sanitizer overhead converted directly into bug count without false negatives. — [arXiv](https://arxiv.org/abs/2402.16497)

#### SEMINAL (2017–2023)

- **Fuzzing: On the Exponential Cost of Vulnerability Discovery** — Marcel Böhme, Brandon Falk; ESEC/FSE 2020 (28th ACM Joint European Software Engineering Conference and Symposium on the Foundations of Software Engineering), 8–13 November 2020, DOI 10.1145/3368089.3409729. Derived from **over four CPU-years** of campaigns on almost three hundred open-source programs, two state-of-the-art greybox fuzzers, four coverage measures and two vulnerability-discovery measures. **First law:** "A non-deterministic fuzzer that generates exponentially more inputs per minute discovers only linearly more new species or less" — for every *additional* bug you want in 24 hours, you need roughly **twice** as many machines. **Second law:** "A non-deterministic fuzzer that generates exponentially more inputs per minute discovers the same number of species also exponentially faster" — 2× machines finds the *same* bugs in ½ the time. — [author PDF](https://mboehme.github.io/paper/FSE20.EmpiricalLaw.pdf); [ACM DL](https://dl.acm.org/doi/10.1145/3368089.3409729); [dataset](https://figshare.com/articles/dataset/Fuzzing_On_the_Exponential_Cost_of_Vulnerability_Discovery/11911287)
- **Profile-Driven System Optimizations (CCS 2023)** gives the most complete end-to-end evidence in the systems line. On **18 MAGMA bugs across 6 projects**, PM_REC_VOS found: AFL **14 bugs** (vs. 11 fork server, 9 native persistent), AFL++ **18 bugs** (vs. 14 fork server, 15 native persistent). Time-to-trigger: AFL **3.71× faster** than fork server and 1.66× faster than native persistent; AFL++ **6.43× faster** than fork server and 2.11× faster than native persistent. Concrete: libxml2 XML017 5 min → 28–32 s; libtiff TIF007 5 hours → 1–3 min; openssl SSL002 8 min → 5–6 min. Also 9 unique bugs in 24 h on bash/mjs/optipng/tidyhtml. Coverage: +8.8% (AFL) / +9.0% (AFL++) over fork server. — [Utah PDF](https://futures.cs.utah.edu/papers/23CCS.pdf)
- **HeXcite (CCS 2021)**: time-to-exposure **52.4% faster** than UnTracer and **48.9% faster** than QEMU; **+12% more unique bugs** than UnTracer; crashes up **997%** vs. QEMU and **1193%** vs. Dyninst. — [arXiv PDF](https://arxiv.org/pdf/2209.03441)
- **ZAFL (USENIX Sec 2021)**: crash-finding improved **26–96%** vs. AFL-Dyninst and **37–131%** vs. AFL-QEMU on LAVA-M and real-world targets — i.e. the throughput gain (48–203%) translated into a comparable-magnitude crash gain. — [USENIX PDF](https://www.usenix.org/system/files/sec21fall-nagy.pdf)
- **ASan-- (USENIX Sec 2022)**: 40–60% speedup translated into **+5–9% branch coverage**; deployed in Chromium for four weeks with no significant slowdown and "detected all the bugs reproduced from previous reports" (i.e. no loss of detection power). — [USENIX PDF](https://www.usenix.org/system/files/sec22summer_zhang-yuchen.pdf)
- **SnapFuzz**: 24.6× mean throughput reproduced all AFLNet-found crashes **plus 12 extra crashes** in 24 h campaigns across 5 applications. — [arXiv PDF](https://arxiv.org/pdf/2201.04048)
- **SoK: Prudent Evaluation Practices for Fuzzing** — Moritz Schloegel, Nils Bars, Nico Schiller, Lukas Bernhard, Tobias Scharnowski, Addison Crump et al.; IEEE Symposium on Security and Privacy (S&P) 2024; arXiv:2405.10220. Systematically analyzes the evaluations of **150 fuzzing papers published at top venues 2018–2023**, and prescribes measuring significance and effect size with established statistical techniques and discussing threats to validity. This is the methodological standard the user's ARVO time-to-bug evaluation will be held to. — [arXiv](https://arxiv.org/abs/2405.10220); [Oakland SoK mirror](https://oaklandsok.github.io/papers/schloegel2024.pdf)

### Inferences

- **The single most useful framing for the user:** Böhme & Falk's *second* law says a throughput multiplier of *k* reduces time-to-a-given-bug by roughly *k*. That makes **time-to-bug on known ARVO bugs the theoretically correct metric** for a throughput paper — far more defensible than "new bugs found in 24 h," which the *first* law says will move only logarithmically. The user should cite this explicitly to justify the ARVO time-to-bug design.
- Empirically, the ratio "time-to-bug speedup / throughput speedup" in published work is well below 1 but not tiny: ClosureX 1.9×/3.53× ≈ 0.54; CCS'23 AFL++ 6.43×/4.81× (381% speedup) ≈ 1.3 (slightly superlinear, likely because faster execution also changes seed scheduling); HeXcite 1.52×/2.8× ≈ 0.54. A reasonable expectation for the user is **roughly half the throughput multiplier showing up as time-to-bug improvement**.
- Nobody in the throughput literature evaluates on **ARVO / historical OSS-Fuzz bugs**. MAGMA (CCS'23), LAVA-M (ZAFL), FuzzBench (Pogofuzz, PeAR) and self-collected 0-days (ClosureX) are the norm. The user's ARVO-based time-to-bug evaluation is therefore methodologically distinctive and worth foregrounding.

### Gaps

- I found no study that isolates the causal effect of throughput alone (holding mutation strategy, seed scheduling and coverage metric fixed) on time-to-bug across many targets. Every throughput paper confounds throughput with some secondary effect (different coverage granularity, different scheduling, different sanitizer set).
- The 1-million-sessions TSE 2025 study, despite being the largest OSS-Fuzz analysis available, does not report execs/sec at all, so it cannot be used to argue that throughput drives bug discovery in production OSS-Fuzz.

## Key Question 5: What is known about where fuzz-target CPU time actually goes (profiling studies of fuzz targets)?

### Takeaway

There is exactly **one rigorous published breakdown** — the CCS 2023 profiling study — and its headline number is the most important fact for the user's positioning: **84% of a fuzzing iteration is spent executing the target itself**, versus 12% in the fuzzer's scheduling/mutation and only 4% in `fork()`. That is a direct, citable justification for attacking the target's own computation rather than the fuzzing apparatus.

### Cited Findings

#### SEMINAL (2017–2023) — the primary data point

- **Profile-Driven System Optimizations for Accelerated Greybox Fuzzing** (CCS 2023) ran a quantitative study on AFL over **12 OSS-Fuzz benchmark programs**, instrumenting AFL to time three stages of each iteration and running 24 h campaigns on both SSD and tmpfs, using `perf` to count page faults and `strace` to trace syscalls. Breakdown in fork-server mode:
  - **Target execution: 84%** of iteration time
  - **Scheduling / mutation / test-case preparation: 12%**
  - **`fork()`: 4%**
  - tmpfs instead of SSD reduces iteration time by only **~2%**
  - In persistent mode, **system calls account for 16.72% of total program execution time**, and **file operations comprise 85%+ of syscalls** in the benchmarked applications
  - Page faults under fork-server mode average **55% higher** than under snapshot mode
  — [Utah PDF](https://futures.cs.utah.edu/papers/23CCS.pdf); [ACM DL](https://dl.acm.org/doi/10.1145/3576915.3616636)
- **UnTracer (S&P 2019)** measured the other half of the picture — how little of the work is useful: coverage-increasing test cases are, on average, **0.0062%** of all test cases for AFL-Clang, **0.0257%** for AFL-QEMU, and **0.00653%** for Driller-AFL. So >99.99% of tracing work is discarded. — [arXiv PDF](https://arxiv.org/pdf/1812.11875)
- **ASan-- (USENIX Sec 2022)** localized sanitizer cost: ASan's >1× runtime overhead "is mainly caused by the extensive sanitizer checks on memory accesses." — [USENIX PDF](https://www.usenix.org/system/files/sec22summer_zhang-yuchen.pdf)
- **PTrix (AsiaCCS 2019)** localized hardware-tracing cost: naive Intel-PT fuzzing's "poor performance [was] caused by the slow extraction of code coverage information from highly compressed PT traces," not by tracing itself. — [arXiv](https://arxiv.org/abs/1905.10499)
- **Xu et al. (CCS 2017)** localized multi-core cost: file system contention and `fork()` scalability, causing a **24× slowdown at 120 cores**. — [ACM DL](https://dl.acm.org/doi/10.1145/3133956.3134046)
- **Practitioner profiling norms**: google/fuzzing's `good-fuzz-target.md` explicitly instructs authors to "profile fuzz targets and eliminate any obvious hot spots," and sets the 1000 exec/s (10000 for lightweight targets) expectation; <10 exec/s means "you are probably doing something wrong." Chromium sets the 1,000 exec/s submission bar. Disk I/O is called out as a bottleneck "especially when conducting many fuzzing experiments on a server simultaneously." — [google/fuzzing docs](https://github.com/google/fuzzing/blob/master/docs/good-fuzz-target.md); [Chromium efficient_fuzzing.md](https://chromium.googlesource.com/chromium/src/+/main/testing/libfuzzer/efficient_fuzzing.md)

#### RECENT (2024–2026)

- **cuFuzz** (arXiv:2603.12485, March 2026) "quantif[ies] execution time overheads of different components" of GPU fuzzing — a component-level time budget, but for CUDA, not C/C++ CPU targets. — [arXiv](https://arxiv.org/abs/2603.12485)
- **The Things That Count: Coverage Evaluation Under the Microscope** — Tobias Holl, Leon Weiß, Kevin Borgolte (Ruhr University Bochum); FUZZING 2026 @ NDSS. Examines the reliability of the coverage-analysis pipeline itself; relevant as a companion to Pogofuzz from the same group. — [NDSS FUZZING 2026 program](https://www.ndss-symposium.org/ndss-program/fuzzing-2026/)
- **Pogofuzz (FUZZING 2026)** uses per-input profile data (weighted by fuzzer power schedule) as its *input*, which is an implicit profiling study of fuzz-target hot code, but it does not publish a CPU-time breakdown. — [paper PDF](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf)

### Inferences

- The 84% figure is the single strongest quantitative warrant for the user's whole premise. Combined with the fact that CCS'23's own optimizations only attacked the other 16% (fork + syscalls) plus persistent-mode enablement, it means the largest slice of fuzzing CPU time has never been directly optimized by the research community.
- The gap between "84% of time is in the target" and "the literature almost exclusively optimizes the remaining 16% plus instrumentation" is the paper-sized hole the user is filling. It is worth stating in exactly those terms.
- The extreme rarity of coverage-increasing inputs (0.0062%) also supports the user's "tiny inputs" premise indirectly: nearly all executions are on near-duplicate, small, malformed inputs, so specializing data structures and caching for that distribution should pay off broadly.

### Gaps

- **No published per-function or per-hotspot profile of OSS-Fuzz targets under real fuzzer-generated inputs exists that I could find.** The CCS'23 study is stage-level (fuzzer / fork / target), not function-level within the target. If the user's profiling pass produces such a breakdown across many ARVO targets, that dataset is itself a novel contribution.
- No study quantifies what fraction of a fuzz target's per-execution work is input-invariant (re-parsing static tables, re-initializing constant structures, re-reading config) versus genuinely input-dependent.
- I found no profiling study of libFuzzer/in-process targets specifically (all the breakdowns above are AFL/AFL++ fork-server based), so the 84/12/4 split may not transfer to OSS-Fuzz's default libFuzzer mode, where fork cost is already zero and the target's share should be even higher.
