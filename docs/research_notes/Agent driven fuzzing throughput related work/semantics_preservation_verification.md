# Semantics-Preservation Verification for Automated / AI-Generated Code Changes, and Optimizations That Hide Bugs

> Scope note for the report writer: this file covers (a) formal and testing-based equivalence verification, (b) how 2025–2026 work validates LLM code changes, (c) documented cases of optimizations deleting or masking security-relevant behavior, (d) mutation testing's relation to "did the change weaken bug detection", and (e) whether anyone has published a methodology for *crash-behavior* preservation specifically. Recent work (2024–2026) is labeled **[RECENT]**; foundational work is labeled **[FOUNDATIONAL]**. Anything I could not confirm against a venue/primary page is marked **UNVERIFIED**.
>
> **Direction-of-implication vocabulary the user needs (important framing):** the user's safety property is *not* equivalence and *not* refinement. It is **failure/crash reflection**: `crash(orig, x) ⟹ crash(opt, x)`. Classic compiler correctness (CompCert-style backward simulation) proves the opposite direction and, critically, is **vacuous on programs with undefined behavior** — which is exactly the population of programs a fuzz target explores. See Q6.

## Q1. Equivalence checking and translation validation for compiler optimizations: what can they verify, at what scale, and would any apply to source-level rewrites of real C/C++ libraries?

### Takeaway
Formal equivalence checking is mature and genuinely trustworthy but almost entirely **function-level, IR-level, and bounded** — Alive/Alive2 verify individual LLVM peephole/IR transformations with an SMT solver and cannot be pointed at an OSS-Fuzz project; the only tool in this family demonstrated at whole-C-project scale is **DiffKemp**, which achieves it by giving up completeness (near-syntactic LLVM-IR comparison plus a library of semantics-preserving patterns) and will simply report "different" for an algorithmic rewrite. No published technique can prove a hand-written algorithmic rewrite of a real C/C++ library equivalent to the original.

### Cited Findings

**[FOUNDATIONAL] Translation validation (the origin of the vocabulary)**
- Translation validation was introduced by Amir Pnueli, Michael Siegel and Eli Singerman, "Translation validation", **TACAS 1998**, LNCS 1384, pp. 151–166 — validate each individual compiler *run* rather than verify the compiler once — [Springer/TACAS 1998](https://link.springer.com/chapter/10.1007/BFb0054170); [summary](https://alastairreid.github.io/RelatedWork/papers/pnueli:tacas:1998/)
- George C. Necula, "Translation Validation for an Optimizing Compiler", **PLDI 2000** (ACM SIGPLAN Notices 35(5)) — [Berkeley PDF](https://people.eecs.berkeley.edu/~necula/Papers/tv_pldi00.pdf); [ACM](https://dl.acm.org/doi/10.1145/358438.349314)
- Martin Rinard, "Credible compilation", MIT-LCS-TR-776, **1999** (technical report, not a conference paper) — reported in the search corpus alongside Pnueli/Necula as the third foundational approach — [context](https://people.eecs.berkeley.edu/~necula/Papers/tv_pldi00.pdf) **(UNVERIFIED: I did not fetch the MIT TR itself)**
- Zuck et al., "VOC: A Methodology for the Translation Validation of Optimizing Compilers", **J.UCS 9(3)** — [PDF](https://www.jucs.org/jucs_9_3/voc_a_methodology_for/Zuck_L.pdf)

**[FOUNDATIONAL] Alive (peephole optimizations)**
- N. Lopes, D. Menendez, S. Nagarakatte, J. Regehr, "Provably Correct Peephole Optimizations with Alive", **PLDI 2015** — a DSL for writing LLVM InstCombine-style peephole optimizations that is automatically proved correct (or given a counterexample) with the **Z3 SMT solver**, then compiled to C++ for inclusion in LLVM — [PLDI 2015 program page](https://pldi15.sigplan.org/details/pldi2015-papers/31/Provably-Correct-Peephole-Optimizations-with-Alive); [CACM Feb 2018 version](https://people.cs.rutgers.edu/~santosh.nagarakatte/papers/cacm-feb-2018.pdf)
- Scope is explicitly *local rewriting*: "peephole optimizations… perform local rewriting to improve the efficiency of LLVM code… individually difficult to get right, particularly in the presence of undefined behavior" — [CACM 2018 PDF](https://web.ist.utl.pt/nuno.lopes/pubs/alive-cacm18.pdf)
- Follow-ons show the narrowness of the scope: termination checking for Alive optimizations (Menendez & Nagarakatte, ICSE 2016) — [PDF](https://people.cs.rutgers.edu/~sn349/papers/icse2016-alive-loops.pdf); LifeJacket for floating-point peepholes — [arXiv 1603.09290](https://arxiv.org/pdf/1603.09290)

**[FOUNDATIONAL] Alive2 (bounded translation validation for LLVM IR)**
- Nuno P. Lopes, Juneyoung Lee, Chung-Kil Hur, Zhengyang Liu, John Regehr, "Alive2: Bounded Translation Validation for LLVM", **PLDI 2021, pp. 65–79** — [PLDI 2021 program page](https://pldi21.sigplan.org/details/pldi-2021-papers/5/Alive2-Bounded-Translation-Validation-for-LLVM); [ACM DOI 10.1145/3453483.3454030](https://dl.acm.org/doi/10.1145/3453483.3454030); [author PDF](https://users.cs.utah.edu/~regehr/alive2-pldi21.pdf)
- **Explicitly bounded**: "limits resource consumption by, for example, unrolling loops up to some bound, which means there are circumstances in which it misses bugs." It is fully automatic via an SMT solver, avoids false alarms, and requires no changes to LLVM — [PLDI 2021 page](https://pldi21.sigplan.org/details/pldi-2021-papers/5/Alive2-Bounded-Translation-Validation-for-LLVM)
- Results: run over **LLVM's unit test suite**, it found **47 new bugs (28 fixed)** and produced **8 patches to the LLVM Language Reference** — [PLDI 2021 page](https://pldi21.sigplan.org/details/pldi-2021-papers/5/Alive2-Bounded-Translation-Validation-for-LLVM)

**[RECENT] Translation validation is still being pushed, and still per-transformation**
- **Trivet** — "LLVM Translation Validation Automated with Large Language Models and Lean", Chunhao Liao et al., **arXiv:2609.19583, Sept 2026**. Combines an LLM with the **Lean** kernel so "every successful verdict [is] checked by the Lean kernel". On **148 LLVM transformations: 147 verified or refuted (99.3%)**, including **60 loop-free transformations with symbolic bitwidths** and **27 cases from a restricted class of loop-containing transformations** that Alive2 struggles with. Proof scaffolding enabled 26 additional proofs and cut mean proof time 75.9% / cost 88% — [arXiv:2609.19583](https://arxiv.org/abs/2609.19583)
- **Optimization-Directed Compiler Fuzzing for Continuous Translation Validation**, **PLDI 2025** (Proc. ACM Program. Lang., DOI 10.1145/3729275) — [ACM](https://dl.acm.org/doi/10.1145/3729275); [KAIST PDF](http://prosys.kaist.ac.kr/publications/pldi25.pdf) **(UNVERIFIED: I could not parse the PDF; only venue/DOI confirmed from the ACM landing page title and the KAIST filename `pldi25.pdf`)**

**[FOUNDATIONAL] Relational / regression verification (two program *versions*, not compiler passes)**
- **RVT** (Regression Verification Tool) pioneered *modular* regression verification: it abstracts equivalent matched callees as **shared uninterpreted functions**, so the proof holds for any consistent interpretation; it proves *partial equivalence* (same outputs for all inputs on which both terminate) — [as described in arXiv:2607.10291](https://arxiv.org/pdf/2607.10291); original: Godlin & Strichman, "Regression verification: proving the equivalence of similar programs" **(UNVERIFIED venue/year)**
- **SymDiff**: "a language-agnostic tool for equivalence checking and displaying semantic (behavioral) differences over imperative programs", operating at the level of the **Boogie** intermediate verification language, with front-ends from C, C# and x86 — [Microsoft Research PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/paper-44.pdf) **(UNVERIFIED venue/year — commonly cited as CAV 2012; I did not confirm)**
- **Reve/LLREVE** encodes paired programs as **constrained Horn clauses** and infers *coupling predicates* relating the two versions' states; SymDiff and DAC instead use a **relational summary** — a single predicate over the disjoint union of both versions' inputs and outputs — [as surveyed in arXiv:2607.10291](https://arxiv.org/pdf/2607.10291)
- Key limitation stated in the same survey: "Regression-verification-based tools, such as SymDiff and RVT, **can only prove equivalence but cannot disprove it**" — [arXiv:2607.10291](https://arxiv.org/pdf/2607.10291)
- **ARDiff**: "Scaling Program Equivalence Checking via Iterative Abstraction and Refinement of Common Code" — prunes common code by iterative abstraction–refinement, **Java only**; Badihi, Li et al. — [NTU PDF](https://www3.ntu.edu.sg/home/yi_li/files/Badihi2020ASP.pdf) **(UNVERIFIED venue — widely cited as ESEC/FSE 2020)**
- **PEQcheck / PEQtest** target *localized refactorings* through segment-level encodings; **PASDA** adds partition-based heuristics for undecided cases — [as surveyed in arXiv:2607.10291](https://arxiv.org/pdf/2607.10291)
- **Client-specific** scaling: Mora et al., "Scaling Client-Specific Equivalence Checking via Impact Boundary Search", **ASE 2020** — restricts the equivalence obligation to what a specific client can observe — [Berkeley PDF](https://people.eecs.berkeley.edu/~fmora/ase20.pdf) **(venue/year taken from the paper's own filename/header `ase20.pdf`; UNVERIFIED against the ASE program)**

**The one technique demonstrated at real-C-project scale: DiffKemp**
- Malík & Vojnar, "Automatically Checking Semantic Equivalence between Versions of Large-Scale C Projects", **ICST 2021** — [ICST 2021 PDF](https://www.fit.vut.cz/person/vojnar/public/Publications/mv-icst21-diffkemp.pdf); journal extension in **ACM TOSEM** (DOI 10.1145/3801958) — [ACM](https://dl.acm.org/doi/10.1145/3801958)
- Method: compile both versions' functions to **LLVM IR**, apply code transformations, then compare **instruction-by-instruction**; where that fails, apply a **built-in or user-supplied semantics-preserving pattern** — [ICST 2021 PDF](https://www.fit.vut.cz/person/vojnar/public/Publications/mv-icst21-diffkemp.pdf)
- **Scalability claim (the number the user wants):** DiffKemp "is able to analyse semantic equivalence of code of the size of the **Linux kernel in the order of minutes** while providing a very low number of false positive results"; applied to both RHEL and upstream kernels — [ICST 2021 PDF](https://www.fit.vut.cz/person/vojnar/public/Publications/mv-icst21-diffkemp.pdf); [Red Hat Research writeup](https://research.redhat.com/wp-content/uploads/2023/02/DiffKemp_-Automatic-Analysis-of-Semantic-Differences-in-Kernel-Versions.pdf); [tool](https://github.com/diffkemp/diffkemp)
- Explicitly framed as "a **light-weight** approach for checking semantic equivalence of program versions obtained by **refactoring** that is much more scalable than other existing approaches" — [ICST 2021 PDF](https://www.fit.vut.cz/person/vojnar/public/Publications/mv-icst21-diffkemp.pdf)

**[RECENT] Contract-based regression verification with LLM-inferred specs**
- "Partial Contracts Suffice: Sound, LLM-Inferred Regression Verification", Charalambous, Menezes, Sun, Cordeiro, **arXiv:2607.10291, July 2026**. Core claim: "a **partial, caller-sufficient contract**, rather than a full behavioral specification, is enough" to verify a patch soundly; contracts are inferred automatically **from counterexamples**, no separate spec step. Targets **C**. Evaluated on Frama-C-Problems and **EqBench-C**. Reports **zero false proofs**, certifies "**safety-preserving conditional equivalence**", matches AutoSpec/Preguss verification rates, and finds **nine pairs that EqBench mislabels as equivalent** — [arXiv:2607.10291](https://arxiv.org/abs/2607.10291)
- **[RECENT] HEC: Equivalence Verification Checking for Code …**, **USENIX ATC 2025** — [USENIX PDF](https://www.usenix.org/system/files/atc25-yin.pdf) **(UNVERIFIED: PDF would not parse; I have only the USENIX-hosted filename `atc25-yin.pdf` establishing ATC '25. Title truncated in the search index. Do not cite details.)**

**[FOUNDATIONAL] Verified compilation as the alternative to validation**
- CompCert (Leroy), "Formal Verification of a Realistic Compiler", **CACM 2009** — [CACM](https://cacm.acm.org/research/formal-verification-of-a-realistic-compiler/)
- Crucial caveat for this project: CompCert's guarantee is that "**specifications that exclude 'going wrong' behaviors (safety-enforcing specifications) are preserved**" — i.e. the theorem says nothing useful once the source program *does* go wrong — [CompCert Complements documentation](https://compcert.org/doc/html/compcert.driver.Complements.html)

### Inferences
- **Scalability verdict per technique (direct answer to the constraint):**
  - Alive / Alive2 / Trivet: **single functions or single IR transformations**, bounded loops, SMT/Lean back end. *Cannot* be run over an OSS-Fuzz project. Useful to the user only as vocabulary ("bounded translation validation") and as a precedent that even *peephole* correctness needed a research program.
  - SymDiff / RVT / Reve / ARDiff / PEQcheck / PASDA: **procedure-level**, small programs, often language-restricted (ARDiff = Java). Not applicable to a whole C/C++ library; possibly applicable to a *single hot function* the agent rewrites, if it is loop-simple and side-effect-light.
  - DiffKemp: **whole-project scale (Linux kernel, minutes)**, but its power comes from near-syntactic IR matching plus a pattern library. It is designed for *refactorings*, not for algorithmic rewrites. For the user's "behavior-preserving algorithmic rewrite" category it would report a difference and demand a hand-written pattern.
  - Mora et al. impact-boundary / client-specific equivalence: the closest formal analogue to "equivalent *as observed by the fuzz harness*", which is the natural weakening the user's setting permits.
- The user's "bit-exact memoization" category is the one class of rewrite where a *mechanical* argument is available: memoization is a classic instance where a relational proof reduces to "the memo table is a function of the same key" — but I found no paper that does this specifically for C/C++ at library scale.
- A practically deployable formal story for this project would be: (i) restrict the optimized region to one function, (ii) emit LLVM IR for both, (iii) run Alive2 *on the extracted function pair* if it is loop-bounded, or DiffKemp-style pattern matching otherwise. Neither gives a whole-project guarantee.

### Gaps
- I found **no technique that proves equivalence of an algorithmic rewrite of a real C/C++ library**. Every tool at project scale is either syntactic/pattern-based (DiffKemp) or testing-based.
- Exact venues for SymDiff, RVT, ARDiff, and Mora et al. are **UNVERIFIED**; the report writer should confirm before citing.
- I could not extract the HEC (USENIX ATC '25) or PLDI 2025 optimization-directed-fuzzing details (PDFs unparseable in this environment).

## Q2. Differential testing for equivalence: EqBench/EquiBench, differential fuzzing, and the state of the art for showing two versions of a real program behave identically

### Takeaway
There is no sound scalable method, so the field's *de facto* answer is **differential execution on generated inputs**, and the newest evidence (2026) is that this is strictly stronger than test suites: differential fuzzing of LLM refactorings found **19–35% non-equivalent** outputs and showed **21% of the non-equivalent cases pass the project's existing tests**. Benchmarks exist (EqBench 2021 for tools, EquiBench 2025 for LLMs) but are small and, per a 2026 paper, contain **mislabeled pairs**.

### Cited Findings

**Benchmarks**
- **[FOUNDATIONAL] EqBench**: "EQBENCH: A Dataset of Equivalent and Non-equivalent Program Pairs", Sahar Badihi et al., **MSR 2021 Data Showcase** — **147 equivalent and 125 non-equivalent** cases (272 pairs total), captured in **both C and Java** — [MSR 2021 page](https://2021.msrconf.org/details/msr-2021-data-showcase/15/EQBENCH-A-Dataset-of-Equivalent-and-Non-equivalent-Program-Pairs); [IEEE Xplore](https://ieeexplore.ieee.org/document/9463140/); [author PDF](https://people.ece.ubc.ca/mjulia/publications/EQBench_2021.pdf); [repo](https://github.com/shrBadihi/EqBench)
- **[RECENT] EquiBench** (different project, LLM-facing): Anjiang Wei et al., **arXiv:2502.12466**, Feb 2025 (latest version Sept 2025; appears to be a preprint, **UNVERIFIED conference acceptance**). **2400 program pairs, 4 languages, 6 categories**, generated by program analysis, compiler scheduling and superoptimization. Across **19 state-of-the-art models**, "in the most challenging categories, the best accuracies are **63.8% and 76.2%**, only modestly above the **50% random baseline**"; models "often rely on **syntactic similarity** rather than… robust reasoning about program semantics" — [arXiv:2502.12466](https://arxiv.org/abs/2502.12466)
- EquiBench's own framing of prior art: "the earlier EQBENCH is too small (272 pairs) for LLM evaluation, while SeqCoBench relies only on statement-level syntactic changes" — [arXiv:2502.12466](https://arxiv.org/html/2502.12466)
- **[RECENT]** EqBench is not gold: the partial-contracts paper reports **nine EqBench pairs mislabeled as equivalent** — [arXiv:2607.10291](https://arxiv.org/abs/2607.10291)

**[RECENT] Differential fuzzing as an equivalence oracle — the single most on-point paper for this project**
- Simantika Bhattacharjee Dristi and Matthew B. Dwyer, "**A Differential Fuzzing-Based Evaluation of Functional Equivalence in LLM-Generated Code Refactorings**", **arXiv:2602.15761, submitted 17 Feb 2026** (cs.SE preprint) — [arXiv:2602.15761](https://arxiv.org/html/2602.15761v1)
- Method: instead of predefined tests, "execute and compare **thousands of automatically generated test inputs**" to detect semantic divergence between original and refactored code
- Results across six LLMs (CodeLlama, Codestral, StarChat2, Qwen-2.5, Olmo-3, GPT-4o), three datasets, two refactoring types: **19–35% of refactorings produce functionally non-equivalent code**, and **21% of the non-equivalent refactorings evade detection by existing test suites**; the authors conclude "reliance on existing tests might **overestimate** functional equivalence" — [arXiv:2602.15761](https://arxiv.org/html/2602.15761v1)
- General framing of the technique: differential fuzzing generates inputs, runs them through both implementations in parallel, and triages discrepancies; it is "similar to fuzzing but with a much **stronger oracle** … because comparing the two outputs means checking the functional behavior of the two implementations" — [Differential Fuzzers overview](https://www.emergentmind.com/topics/differential-fuzzers)
- Recent work "developed differential fuzzing-based equivalence checkers that … need **no predefined test cases** and can explore a much larger input space" than test-based evaluation — [Differential Fuzzers overview](https://www.emergentmind.com/topics/differential-fuzzers)

**[FOUNDATIONAL] Differential testing of compilers = the same idea at compiler scale**
- **EMI** (Equivalence Modulo Inputs): Vu Le, Mehrdad Afshari, Zhendong Su, "Compiler validation via equivalence modulo inputs", **PLDI 2014** — profile a program's test executions and stochastically prune its **unexecuted** code, producing variants that must behave identically on those inputs — [ACM DOI 10.1145/2594291.2594334](https://dl.acm.org/doi/10.1145/2594291.2594334); [PDF](https://fm.csl.sri.com/SSFT14/PLDI14-Orion.pdf); [project page](https://web.cs.ucdavis.edu/~su/emi-project/)
- EMI yielded "**147 confirmed, unique bug reports for GCC and LLVM alone**, with the majority … miscompilations, and more than 100 already fixed" — [project page](https://web.cs.ucdavis.edu/~su/emi-project/)
- EMI tool lineage: **Orion** (delete statements in dead regions), **Athena** (MCMC), **Hermes** (insert code into live regions) — [arXiv survey context](https://arxiv.org/pdf/1610.03148)
- **DifFuzz**: differential fuzzing applied to side-channel analysis (two runs of the *same* program on different secrets) — the other major use of the "differential fuzzing" term, useful for disambiguation — [arXiv:1811.07005](https://arxiv.org/pdf/1811.07005)

**[RECENT] Checksum-based differential evaluation for C**
- 2025–2026 work uses **Csmith**-generated compilable C programs with **integrated checksum logic** as a more reliable semantic-equivalence oracle than string-similarity metrics for code translation — [Beyond BLEU: A Semantic Evaluation Method for Code Translation, arXiv:2605.05282](https://arxiv.org/html/2605.05282) **(UNVERIFIED: abstract read via search summary only)**

### Inferences
- The state of the art for "show two versions of a *real* program are observably equivalent" is **differential execution with an aggressive input generator**, not proof. The user's bidirectional crash cross-check is already an instance of this, and Dristi & Dwyer (arXiv:2602.15761) is the citation that justifies preferring it to "the test suite still passes".
- The 21%-evade-tests number is the strongest single quantitative argument the user has for *not* trusting a project's unit tests as the semantics oracle for an LLM rewrite.
- The user's setting has an advantage over generic differential fuzzing: the fuzz harness *is* the input generator and the crash signal *is* the observable, so a corpus replay on both binaries is a cheap, high-coverage differential test. The natural strengthening is to make the differential comparison run **continuously during fuzzing** (both binaries fed the same mutated inputs) rather than only on saved crash artifacts.
- Because EquiBench shows LLMs are near-chance at judging equivalence in hard categories, an "LLM reviewer says it's equivalent" gate is not defensible; the user should cite this against any self-verification design.

### Gaps
- I found **no benchmark of equivalence for C/C++ *library-scale* rewrites** — EqBench/EquiBench are small snippets/functions.
- No paper measured false-negative rate of differential fuzzing as an equivalence oracle (how many real inequivalences it misses) on real C libraries.

## Q3. Correctness of LLM-generated code changes: how do 2025–2026 papers validate that an LLM refactoring/optimization did not change behavior, and what failure rates are reported?

### Takeaway
The dominant validation method is still **"run the existing test suite"**, and every paper that looks harder finds that this over-reports correctness. Reported failure rates for LLM performance/refactoring edits cluster in the **20–57%** range depending on model and setting, with the most rigorous (differential-fuzzing) study at **19–35% semantically non-equivalent**.

### Cited Findings

**[RECENT] Performance-optimization agents on real repositories**
- **SWE-Perf**: "Can Language Models Optimize Code Performance on Real-World Repositories?", **arXiv:2507.12415** (v2), **140 instances** derived from real performance-improving pull requests across **9 Python repos** (astropy, requests, scikit-learn, …); each instance ships the codebase, target functions, performance tests, expert patches and an executable environment — [arXiv:2507.12415](https://arxiv.org/html/2507.12415v2); [GitHub](https://github.com/SWE-Perf/SWE-Perf); listed as an **ICML 2026 poster** — [ICML virtual page](https://icml.cc/virtual/2026/poster/61514)
- **Correctness oracle = unit tests only**: "the patch preserves the functional correctness of the code, specifically whether **all unit tests pass** successfully after the patch is applied" — [arXiv:2507.12415v2](https://arxiv.org/html/2507.12415v2)
- **Correctness failure rates (Oracle / file-level setting):** Claude-4-Sonnet **26.43% failure** (73.57% correct); GPT-4o **43.57% failure** (56.43% correct); DeepSeek-V3 **57.14% failure** (42.86% correct). Realistic repo-level setting with OpenHands: **22.14% failure** (77.86% correct) — [arXiv:2507.12415v2](https://arxiv.org/html/2507.12415v2)
- SWE-Perf explicitly designs around **"functional pruning"** — the risk that a model, seeing the test, "modif[ies] the code to retain only the functionality exercised by the test." This is exactly the user's "the optimization silently narrows behavior" risk, named in a benchmark paper — [arXiv:2507.12415v2](https://arxiv.org/html/2507.12415v2)
- **[RECENT] Benchmarks themselves are unstable**: "Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents?", Zhi Chen, Zhensu Sun, Yuling Shi, David Lo, Lingxiao Jiang, **arXiv:2607.01211** (July 2026). Reference patches satisfied the benchmarks' own validity rules on replay for only **39/102 GSO**, **11/140 SWE-Perf**, **411/498 SWE-fficiency** tasks; official rankings disagreed on **9 of 28** pairwise comparisons across GSO vs SWE-fficiency — [arXiv:2607.01211](https://arxiv.org/abs/2607.01211)
- Related benchmarks in this space: **GSO** (arXiv:2505.23671), **SWE-fficiency** (arXiv:2511.06090), **PIE / LEARNING PERFORMANCE-IMPROVING CODE EDITS** (ICLR 2024, slow→fast C++ pairs from CodeNet, timed in the **gem5** simulator) — [PIE/ICLR](https://openreview.net/pdf?id=ix7rLVHXyY); **ECCO**: "Can We Improve Model-Generated Code Efficiency **Without Sacrificing Functional Correctness**?" — the paper's own framing is that "no existing method can improve efficiency without sacrificing functional correctness" — [arXiv:2407.14044](https://arxiv.org/pdf/2407.14044); [site](https://ecco-code-eff.github.io/)

**[RECENT] Refactoring-specific behavior-preservation studies**
- **Differential fuzzing study (see Q2)**: **19–35%** of LLM refactorings functionally non-equivalent; **21%** of those evade the existing test suite — [arXiv:2602.15761](https://arxiv.org/html/2602.15761v1)
- **"An empirical study of LLM-based refactoring consistency"**, Zhang, Yuan et al., **Empirical Software Engineering** (Springer, DOI 10.1007/s10664-026-10911-6). Built **DataRef** (468 Java + 544 Python code segments), generated **8,096 refactored segments** with ChatGPT-3.5/4.0, CodeLlama, CodeGeeX. **928 refactored segments exhibit behavioral inconsistencies; 180 cases are outright refactoring failures** — [Springer](https://link.springer.com/article/10.1007/s10664-026-10911-6); [Semantic Scholar](https://www.semanticscholar.org/paper/An-empirical-study-of-LLM-based-refactoring-Zhang-Yuan/0badabb1ce66bdc73824d568d1cb17df5de2b55b)
- **[RECENT] Static proxies are weak**: a refactoring study reports "static preservation proxy rates range from **81.8% to 90.0%**… the checks remain **static proxies and do not prove behavioral equivalence**", with assert/fail-call preservation — the weakest indicator — passing in only **57.1%** of outputs — [Refactoring with LLMs: Bridging Human Expertise and…, arXiv:2510.03914](https://arxiv.org/pdf/2510.03914)
- **[RECENT] LLM-as-behavioral-diff-oracle**: Oliveira, Gheyi, Ribeiro, Garcia, "Detecting Behavioral Changes in Python Refactoring Implementations with Foundation Models", **SBES 2026** (arXiv:2608.09919, Aug 2026). A foundation-model oracle reads git-style diffs to flag behavioral changes; over **1,152 refactoring attempts / 217 transformation pairs** it found **13 distinct bugs across 7 refactoring types** in the **Rope** refactoring tool, **12 of 13 accepted** by developers — [arXiv:2608.09919](https://arxiv.org/abs/2608.09919)

**[RECENT] Validation-first designs for LLM optimization**
- **SeGaBench** — "Can Large Language Models Recover Semantic Optimization Opportunities That Compilers Miss?", Hailong Jiang et al., **arXiv:2608.03983**, Aug 2026. **120 test cases** (100 synthetic, 20 real-world), each shipping **correctness and semantic validators**. Best model: **94.8% of responses produce correct artifacts** (≈**5.2% incorrect**), ≥1.05× speedup in **83.3%** of cases, overall performance success **93.3%**. Authors position LLMs as "**speculative semantic proposers**" that require external validation — [arXiv:2608.03983](https://arxiv.org/abs/2608.03983)
- **[RECENT] LLMs are bad equivalence judges**: an assessment of code understanding reports LLMs fail to judge semantic equivalence in **~41%** of cases with no context and **~29%** with a simple generic context — [arXiv:2504.00065](https://arxiv.org/pdf/2504.00065) **(UNVERIFIED: read via search summary of the PDF, not the paper body)**
- Other 2026 pipelines pairing LLM optimization with a verification loop: "Agentic Code Optimization via Compiler-LLM Cooperation" — [arXiv:2604.04238](https://arxiv.org/abs/2604.04238); "Improving LLM Code Reasoning via Semantic Equivalence Self-Play with Formal Verification" (generator/evaluator self-play with proofs or counterexamples) — [arXiv:2604.17010](https://arxiv.org/html/2604.17010v1); "Semantic Equivalence Verification of HPC Codes Using LLMs" (SCA/HPC Asia workshops; **15,000 code pairs** in Fortran/C/C++/Python) — [ACM DOI 10.1145/3784828.3785337](https://dl.acm.org/doi/10.1145/3784828.3785337)
- **[RECENT] Understanding Agent-Based Patching of Compiler Missed Optimizations**, Batu Guan, Zirui Wang, Shaohua Li, **arXiv:2607.02370** (July 2026): coding agents "often optimize the given examples" but patches show **scope misalignment** — they "cover only part of the developer-intended scope or partially overlap with it," some over-generalizing beyond the reference — [arXiv:2607.02370](https://arxiv.org/abs/2607.02370)

### Inferences
- Across the 2026 literature, **the measured semantic-break rate for LLM code edits is on the order of one in five to one in three**, and the subset that *also* passes the project's tests is non-trivial (21% of breaks in the differential-fuzzing study). For an experiment whose validity depends on the bug still being reachable, this is a first-order threat, not a rounding error.
- Every methodologically strong 2026 paper converges on the same design the user already has: **an external, execution-based validator applied to every accepted change**, with the LLM treated as a *proposer*, not a verifier (SeGaBench's phrase "speculative semantic proposers" is a quotable framing).
- The SWE-Perf "functional pruning" hazard is the closest published name for the user's central fear generalized to functionality: a model that can see the oracle will optimize *toward the oracle*. The user's analogue is an agent that can see the crash check; the mitigation is that the crash cross-check uses artifacts the agent never sees during editing.
- The benchmark-instability result (arXiv:2607.01211) matters for the user's *measurement* side, not the safety side: even the reference patches in the field's best perf benchmarks fail to replay as valid on a different machine, so throughput claims need repeated, same-machine replays (which their fixed-corpus deterministic replay design already does).

### Gaps
- **No paper I found measures how often an LLM optimization changes *crash* behavior specifically** — all failure rates are functional-output failure rates.
- I could not confirm the arXiv:2504.00065 41%/29% figures from the paper body.

## Q4. Compiler optimizations that REMOVE security checks or MASK bugs — precedent that "optimization can hide a bug" is real and documented

### Takeaway
This is one of the best-documented phenomena in systems security. Three independent lines of evidence: (1) **UB-driven dead-code elimination deletes security checks** (Wang et al., STACK, SOSP 2013 — 161 bugs); (2) **dead-store elimination deletes secret-scrubbing memsets** (Yang et al., USENIX Security 2017); and, most directly on point for a fuzzing experiment, (3) **compiler optimizations delete sanitizer failures, hiding bugs that then cannot be found by fuzzing at all** (Isemann et al., "Don't Look UB", PLDI 2023 — 17 sanitizer-eliding optimizations in Clang, 20 previously-hidden real bugs recovered once they were disabled).

### Cited Findings

**[FOUNDATIONAL] Undefined behavior → optimizations discard security checks (STACK)**
- Xi Wang, Nickolai Zeldovich, M. Frans Kaashoek, Armando Solar-Lezama, "**Towards Optimization-Safe Systems: Analyzing the Impact of Undefined Behavior**", **SOSP 2013** — [MIT PDF](https://people.csail.mit.edu/nickolai/papers/wang-stack.pdf); [SOSP 2013 talk slides](https://sigops.org/s/conferences/sosp/2013/talks/wang_stack_se05_04.pdf)
- Defines **optimization-unstable code ("unstable code")**: "code that is unexpectedly **discarded by compiler optimizations due to undefined behavior** in the program." Consequences: "**security checks can be discarded, weaknesses are amplified, and system behavior becomes unpredictable**"; present in the Linux kernel and Postgres — [MIT PDF](https://people.csail.mit.edu/nickolai/papers/wang-stack.pdf)
- **STACK**, a static checker built on **LLVM** that models ten kinds of undefined behavior, "precisely identifies undefined behavior bugs"; applying it to widely used systems uncovered **161 new bugs that were confirmed and fixed** — [MIT PDF](https://people.csail.mit.edu/nickolai/papers/wang-stack.pdf); journal/extended version — [TOCS version](https://unsat.cs.washington.edu/papers/wang-stack-tocs.pdf)
- Popular-press/summary coverage confirming the framing: [LWN, "Optimization-unstable code"](https://lwn.net/Articles/575563/); [CACM, "A Differential Approach to Undefined Behavior Detection"](https://cacm.acm.org/research/a-differential-approach-to-undefined-behavior-detection/)

**[FOUNDATIONAL] Dead-store elimination removes secret scrubbing**
- Zhaomo Yang, Brian Johannesmeyer, Anders Trier Olesen, Sorin Lerner, Kirill Levchenko, "**Dead Store Elimination (Still) Considered Harmful**", **26th USENIX Security Symposium (USENIX Security '17)**, Vancouver BC, August 2017 — [USENIX presentation page](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/yang); [PDF](https://www.usenix.org/system/files/conference/usenixsecurity17/sec17-yang.pdf); [ACM](https://dl.acm.org/doi/10.5555/3241189.3241269)
- Findings over **11 open-source security projects**: **4 of 11 used flawed scrubbing techniques** that may fail to scrub sensitive data, and **4 additional projects did not use their scrubbing function consistently**. The authors add an **LLVM compiler option** that retains scrubbing operations and publish a best-of-breed scrubbing function — [USENIX page](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/yang)
- Mechanism, stated plainly: DSE "finds memory store operations that are either not used or overwritten and removes those instructions"; "the compiler can assume that isolated calls to memset are not useful, since the memory… will not be read again," leaving sensitive data exposed. C11's **`memset_s`** is the standardized mitigation — [OWASP: Insecure Compiler Optimization](https://owasp.org/www-community/vulnerabilities/Insecure_Compiler_Optimization); [Quarkslab, "Keep my memset"](https://blog.quarkslab.com/a-glance-at-compiler-internals-keep-my-memset.html)
- Real-world instance: [Telegram MTProxy issue #700, "Compiler Optimization Inappropriately Removes Sensitive Memory Clearing"](https://github.com/TelegramMessenger/MTProxy/issues/700)

**[RECENT-ish, 2023] Optimizations delete *sanitizer failures* — the closest published analogue to "an optimization hid the crash"**
- Raphael Isemann, Cristiano Giuffrida, Herbert Bos, Erik van der Kouwe, Klaus von Gleissenthall, "**Don't Look UB: Exposing Sanitizer-Eliding Compiler Optimizations**", **Proc. ACM Program. Lang. 7, Issue PLDI (PLDI 2023), June 2023, DOI 10.1145/3591257** — [PLDI 2023 program page with full abstract](https://pldi23.sigplan.org/details/pldi-2023-pldi/38/Don-t-Look-UB-Exposing-Sanitizer-Eliding-Compiler-Optimizations); [PDF](https://download.vusec.net/papers/dontlookub_pldi23.pdf); [ACM](https://dl.acm.org/doi/10.1145/3591257)
- Verbatim from the abstract: "While sanitizers want to expose undefined behavior, optimizers often exploit these same properties for performance… **optimizations can remove sanitizer failures, thereby hiding the presence of bugs or even introducing new ones.**"
- Quantitative results: **LookUB**, a **differential-testing** framework, found **17 sanitizer-eliding optimizations in Clang**; using static analysis and fuzzing the authors then found "**20 new bugs** in **Linux Containers, libmpeg2, NTFS-3G, and WINE**" that "were **previously hidden due to sanitizer-eliding optimizations**"; their Clang customization mitigates this at **4% overhead** — [PLDI 2023 page](https://pldi23.sigplan.org/details/pldi-2023-pldi/38/Don-t-Look-UB-Exposing-Sanitizer-Eliding-Compiler-Optimizations)
- Corroborating practitioner guidance: at **-O2/-O3** "rearranged code could mask real errors from the sanitizer's memory checks"; **tail-call optimization** must be disabled (`-fno-optimize-sibling-calls`) for accurate ASan stacks; **common subexpression elimination** can replace a pointer dereference with a constant, ignoring that the pointer is no longer a valid allocation; even at **-O0**, constant folding can optimize away UB code — [Trail of Bits, Understanding AddressSanitizer](https://blog.trailofbits.com/2024/05/16/understanding-addresssanitizer-better-memory-safety-for-your-code/); [SoK: Sanitizing for Security, arXiv:1806.04355](https://arxiv.org/pdf/1806.04355)
- LLVM community has an open design thread on the same conflict: [RFC: Safe Optimizations for Sanitizers, LLVM Discourse](https://discourse.llvm.org/t/rfc-safe-optimizations-for-sanitizers/62729)
- Sanitizers themselves have bugs that cause missed reports: **UBfuzz**, "Finding Bugs in Sanitizer Implementations", **ASPLOS 2024** (DOI 10.1145/3617232.3624874) — [ACM](https://dl.acm.org/doi/10.1145/3617232.3624874); [arXiv:2401.04538](https://arxiv.org/pdf/2401.04538)

**Optimization settings change which bugs are findable at all**
- An empirical study of compiler optimization bugs found that "**83.54% of bugs are only detected under custom optimization settings**", i.e. the standard -O0…-O3 levels are not a complete search of behavior space — [as reported in optimization-bug study search results](https://www.sciencedirect.com/science/article/abs/pii/S0164121220302740) **(UNVERIFIED: number read from a search summary; confirm against the ScienceDirect paper before citing)**
- "Compiler fuzzing: how much does it matter?", **OOPSLA 2019** (Proc. ACM Program. Lang., DOI 10.1145/3360581) and its precursor "A Systematic Impact Study for Fuzzer-Found Compiler Bugs" (arXiv:1902.09334): "almost **half** of the [miscompilation] bugs propagate to generated binaries for at least one package, though only a very small part of the binary is typically affected" — [ACM](https://dl.acm.org/doi/10.1145/3360581); [arXiv:1902.09334](https://arxiv.org/html/1902.09334v2)
- OSS-Fuzz's own documentation acknowledges an "unreproducible" bug class arising from "internal state being manipulated over several executions" or "any non-determinism introduced into the application" — [OSS-Fuzz: Reproducing issues](https://google.github.io/oss-fuzz/advanced-topics/reproducing/); [OSS-Fuzz FAQ](https://google.github.io/oss-fuzz/faq/). I found **no** OSS-Fuzz documentation attributing unreproducibility to optimization level specifically.

**Adjacent: removing code removes vulnerabilities (debloating)**
- Brown et al., "A Broad Comparative Evaluation of Software Debloating Tools", **USENIX Security 2024** — debloating "removes code associated with tens of historical vulnerabilities", but the broad evaluation found "consistent and significant improvements in **two metrics only**: binary size and gadget locality, with **marginal benefits at best** for all other performance and security metrics" — [USENIX PDF](https://www.usenix.org/system/files/usenixsecurity24-brown.pdf); [ACM](https://dl.acm.org/doi/10.5555/3698900.3699120)
- SoK framing of the measurement difficulty: security assessment "predominantly revolv[es] around quantifying the count of CVEs and gadgets," and removing previously-unknown reachable vulnerabilities is "generally not possible to evaluate because [it is] undecidable" — [SoK: Software Debloating Landscape and Future Directions](https://www.csl.sri.com/users/gehani/papers/FEAST-2024.Debloat.pdf)

### Inferences
- **The user has an exact, high-prestige precedent.** "Don't Look UB" (PLDI 2023) is the paper to cite for the sentence "an optimization can make a real bug undetectable by a sanitizer-instrumented fuzzer" — it is empirically demonstrated (17 Clang transformations), and the bugs it recovered (20, in LXC/libmpeg2/NTFS-3G/WINE) are precisely bugs that fuzzing had been unable to find while the optimization was in place.
- The user's threat model is strictly *worse* than the compiler case: a compiler applies a fixed, audited set of transformations, whereas an LLM applies unaudited, arbitrary source rewrites. If 17 audited Clang passes can elide sanitizer failures, an unconstrained source rewrite certainly can. This is the strongest available argument for the user's category system.
- Wang et al.'s "unstable code" is the right *term of art* for the user's failure mode at the source level: source changes that alter whether UB is present change what the compiler is licensed to delete, so a source-level "optimization" can turn a previously-triggering UB into either well-defined code (bug masked) or newly-deleted code (crash removed) **without any change to the compiler flags**.
- A practical, citable hardening the user could adopt from this literature: replay crash artifacts on the optimized binary **at multiple optimization levels and with/without the specific Clang mitigations** from Isemann et al., since an optimization-level-sensitive crash is exactly the signature of a sanitizer-eliding interaction.

### Gaps
- I found **no paper measuring how often a *source-level* performance change makes a previously-crashing input stop crashing.** This is an open niche and appears to be a genuinely novel contribution area for the user.
- The 83.54% optimization-settings figure needs verification against the ScienceDirect paper.

## Q5. Mutation testing and "did the change weaken bug detection?"

### Takeaway
Mutation testing is the standard instrument for "does this artifact still detect faults," and there is a 2025 result showing that *purported* semantics-preserving transformations frequently are not (**23 of 39** implemented transformations from the literature actually changed semantics) — but I found **no prior work that uses mutation testing to check that an *optimized* program still detects the same faults as the original**. That specific composition appears unoccupied.

### Cited Findings
- Standard definition: mutation testing "deliberately injects faults (called mutants) into the production code to count how many are caught by tests"; the fraction caught is the **mutation score**, a proxy for fault-detection capability — [Thoughtworks Technology Radar](https://www.thoughtworks.com/radar/techniques/mutation-testing)
- Intuition used to justify it as a bug-detection proxy: "the more artificial bugs a test suite can detect, the more likely it is to detect potential real bugs" — [Efficient Mutation Testing via Pre-Trained Language Models, arXiv:2301.03543](https://arxiv.org/pdf/2301.03543)
- **[RECENT] The negative result most relevant here**: Max Hort, Linas Vidziunas, Leon Moonen, "**Semantic-Preserving Transformations as Mutation Operators: A Study on Their Effectiveness in Defect Detection**", **Mutation 2025 workshop at ICST 2025** (arXiv:2503.23448, 30 Mar 2025). They surveyed **28 publications containing 94 transformations**, implemented **39**, and found "**23 out of 39 transformations change code semantics**". Using only the 16 genuinely semantics-preserving ones in three ensemble strategies gave **no improvement** in vulnerability-detection model accuracy; they conclude that reusing shared "semantic-preserving" transformations is hard and "sometimes introduc[es] unintended semantic changes" — [arXiv:2503.23448](https://arxiv.org/abs/2503.23448)
- The standard (weak) way mutation-adjacent work validates that a variant is semantics-preserving: "the same set of test cases are executed on both the seed bug and its mutants, and if the test results are identical, the mutant is considered a valid semantically equivalent variant" — [arXiv:2503.23448 context](https://arxiv.org/pdf/2503.23448)
- Known structural problems: large mutant counts and the **equivalent mutant problem** are the two standing barriers to applying mutation testing — [Springer chapter on problems of mutation testing / higher-order mutation](https://link.springer.com/chapter/10.1007/978-3-319-06569-4_12)
- Clone-detection analogue showing the same tactic used adversarially: semantic-preserving code transformations used to break ML-based clone detectors — [arXiv:2111.10793](https://arxiv.org/pdf/2111.10793)

**Closest thing to "verify a build still detects the same faults": ground-truth fuzzing benchmarks**
- **Magma: A Ground-Truth Fuzzing Benchmark**, Ahmad Hazimeh, Adrian Herrera, Mathias Payer — **118 bugs spanning 11 CWEs across 7 targets**, evaluated over 200,000 CPU-hours. Bugs are taken from older versions and **forward-ported** to the current version so every planted bug has a ground-truth oracle — [arXiv:2009.01120](https://arxiv.org/abs/2009.01120); [EPFL preprint](https://hexhive.epfl.ch/magma/docs/preprint.pdf); [ACM SIGMETRICS Performance Evaluation Review](https://dl.acm.org/doi/10.1145/3543516.3456276)
- **This is the published precedent for the user's PoC re-verification step**: "Without verification, forward-porting may inject bugs which **cannot be triggered**. Magma uses fuzzing to reduce this possibility… if the forward-ported vulnerability cannot be reached, this represents an **unachievable task**." Magma's monitor reports which planted bug is **reached** vs **triggered** — [arXiv:2009.01120](https://arxiv.org/pdf/2009.01120)
- Follow-ups: "In the Magma chamber: Update and challenges in ground-truth vulnerabilities revival…" — [arXiv:2503.19909](https://arxiv.org/pdf/2503.19909); "The Impact of Magma: A Ground-Truth Fuzzing Benchmark" — [arXiv:2608.28016](https://arxiv.org/pdf/2608.28016) **[RECENT]**

### Inferences
- Magma's **reached vs. triggered** distinction is directly reusable vocabulary for the user: an optimization that preserves *reachability* but destroys *triggerability* (e.g. by making an out-of-bounds read land inside a now-larger buffer, or by memoizing past the faulting call) is precisely the failure they must rule out, and Magma's instrumentation model (a canary condition at the bug site reporting both reached and triggered) is an implementable design for a stronger check than "the binary crashed".
- **A defensible novel method for the user, built entirely from existing pieces:** treat the *original* project as the "mutant-carrying" program, use the known crash artifacts / injected canaries as the fault set, and define the optimized build's **bug-detection-preservation score** = fraction of the original's ground-truth faults still triggered. That is mutation testing's accounting applied to a build rather than a test suite. I found no paper doing this, which is worth stating plainly as a contribution.
- Hort et al.'s 23/39 result is a useful cautionary citation for any claim of the form "this transformation category is behavior-preserving by construction": in the published literature, over half of transformations *labeled* semantics-preserving were not.

### Gaps
- **No prior work found** that applies mutation testing to verify that an optimized/transformed program retains the fault-detection capability of the original. Searched multiple phrasings; results were all about mutation testing *of test suites* or *optimizing mutation testing itself*.
- No work found on mutation testing of fuzz *targets* for the purpose of validating a build change.

## Q6. Any published methodology for proving/arguing that a performance change preserves CRASH behavior specifically?

### Takeaway
**I found no published methodology aimed at crash-behavior preservation under performance optimization.** The literature contains all the ingredients — property-preserving program reduction, robust safety preservation in secure compilation, Magma's PoC verification, LookUB's differential crash-elision testing — but nobody has assembled them into a stated methodology for "this optimization does not reduce crashing." This is the clearest gap in the survey and the user's strongest novelty claim.

### Cited Findings

**The nearest published analogue: property-preserving program reduction ("interestingness test")**
- Program reduction is formally defined as: given a program `P` exhibiting property `ψ`, produce `P'` such that "(i) `P'` **preserves the property φ**, and (ii) `P'` is smaller than `P`" — the canonical `ψ` is "this C program crashes GCC" — [Perses: Syntax-Guided Program Reduction, ICSE 2018](https://helloqirun.github.io/papers/icse18_chengnian.pdf); [SWAG Lab page](https://swag.uwaterloo.ca/publications/perses-syntax-guided-program-reduction.html)
- The property is checked **dynamically, by re-running**, not proved: C-Reduce and Perses "use a delta-debugging-like algorithm whose '**interestingness**' function is defined by the presence or absence of the analysis behavior of interest" — [Static Program Reduction via Type-Directed Slicing, PACMSE](https://dl.acm.org/doi/10.1145/3728968)
- C-Reduce's designers state the crucial point explicitly: "**Only a small proportion of C-Reduce's transformation passes is intended to be semantics-preserving** in the sense that a compiler's optimization passes must be, since the goal is only to **preserve enough semantics to probabilistically avoid breaking whatever property makes a test case interesting**" — [IEEE Software Blog: Design and Evolution of C-Reduce (Part 1)](http://blog.ieeesoftware.org/2019/07/design-and-evolution-of-c-reduce-part-1.html)
- Recent work in the same line: [SimP, arXiv:2608.08352](https://arxiv.org/pdf/2608.08352) **[RECENT]**; [DRReduce, arXiv:2605.19412](https://arxiv.org/html/2605.19412v1) **[RECENT]**; [LPR: LLM-Aided Program Reduction, arXiv:2312.13064](https://arxiv.org/pdf/2312.13064)

**The formal vocabulary for "the transformation must not remove going-wrong behavior"**
- CompCert's theorem preserves only **safety-enforcing specifications**: "any such specification that is satisfied by the source C program is always satisfied by the generated assembly code" — i.e. it says nothing once the source program has UB — [CompCert Complements](https://compcert.org/doc/html/compcert.driver.Complements.html); [Leroy, CACM 2009](https://cacm.acm.org/research/formal-verification-of-a-realistic-compiler/)
- **Robust Safety Preservation (RSP)** is the secure-compilation criterion built precisely to cope with UB: it ensures "any low-level attack against a compiled program's safety properties mounted by compartments **dynamically compromised by undefined behavior** could also have been mounted at the source level" — [When Good Components Go Bad, CCS 2018, arXiv:1802.00588](https://arxiv.org/pdf/1802.00588); [ACM DOI 10.1145/3243734.3243745](https://dl.acm.org/doi/10.1145/3243734.3243745)
- **Trace-relating compiler correctness** generalizes compiler correctness to source/target traces drawn from different sets, which is the formal machinery for relating "crashes at source" to "crashes at target" — Abate et al. — [arXiv:1907.05320](https://arxiv.org/pdf/1907.05320)
- **SECOMP**: formally secure compilation of compartmentalized C, dealing explicitly with UB-induced compromise — [arXiv:2401.16277](https://arxiv.org/pdf/2401.16277) **[RECENT, 2024]**
- Community framing: secure compilation "aims at developing compilers that **preserve the security properties** of the source programs" — [SIGPLAN Blog, Secure Compilation](https://blog.sigplan.org/2019/07/01/secure-compilation/); [Dagstuhl Seminar 18201 report](https://drops.dagstuhl.de/storage/04dagstuhl-reports/volume08/issue05/18201/DagRep.8.5.1/DagRep.8.5.1.pdf)

**The empirical instruments that exist for crash-preservation**
- **LookUB** (PLDI 2023) is, methodologically, exactly a crash-preservation differential test: it searches for optimizer transformations under which a sanitizer failure **disappears** — [PLDI 2023 page](https://pldi23.sigplan.org/details/pldi-2023-pldi/38/Don-t-Look-UB-Exposing-Sanitizer-Eliding-Compiler-Optimizations)
- **Magma** verifies that each forward-ported bug remains **reachable and triggerable** by fuzzing before admitting it to the benchmark — [arXiv:2009.01120](https://arxiv.org/pdf/2009.01120)
- **Partial contracts** (2026) certifies "**safety-preserving conditional equivalence**" — the closest formal phrase I found to the user's property, though it is about a patch preserving safety, not about preserving crashes — [arXiv:2607.10291](https://arxiv.org/abs/2607.10291)

### Inferences
- **Recommended framing for the user's paper.** Their property is not "equivalence" and not "refinement"; state it as a **one-sided, crash-reflecting relation**: for every input `x` in the fuzzer's input space, `crash(orig, x) ⟹ crash(opt, x)` (and ideally the same crash site/type). Note explicitly that:
  1. Standard compiler correctness proves the *converse* containment (target behaviors ⊆ source behaviors) and is **vacuous under UB** (CompCert Complements) — so it is the wrong theorem for this setting;
  2. Two-sided observational equivalence (bisimulation) implies the property but is unachievable at library scale (Q1);
  3. The achievable discipline is the **program-reduction discipline**: define an interestingness/crash predicate and *re-check it empirically on every candidate*, exactly as C-Reduce does — which is what their bidirectional cross-check and PoC re-verification implement. C-Reduce's own designers' quote ("preserve enough semantics to probabilistically avoid breaking whatever property makes a test case interesting") is the best available statement of this epistemic stance and should be quoted.
- **Bidirectionality is the right design and can be motivated formally.** Checking only `crash(orig) ⟹ crash(opt)` admits an optimization that adds *new* crashes (which would inflate the experiment in the other direction, producing false bug discoveries). Checking only the reverse admits masking. Requiring both directions on the artifact set is a finite approximation of bisimulation restricted to the crash observable — a defensible framing, and I found no paper that states it, so the user can claim it.
- **Where the user's design is weaker than the literature suggests it could be:** replaying only *saved crash artifacts* tests the property on a set of inputs chosen before the optimization existed. Dristi & Dwyer's result (21% of semantic breaks evade the existing test set) is the direct warning. The strengthening with published precedent is **continuous differential execution** (feed the live fuzzer's mutated inputs to both binaries and compare the crash observable), plus **Magma-style canaries** at the known bug sites so that "reached but not triggered" is distinguishable from "not reached".

### Gaps
- **No published methodology for proving or systematically arguing crash-behavior preservation under a performance change.** I searched "crash equivalence", "crash-preserving transformation", "bug-preserving optimization", "vulnerability-preserving refactoring" and related phrasings; results were about crash-*consistency* of file systems (an unrelated meaning of "crash") or about generic functional equivalence.
- No study quantifies how often a *source-level* optimization removes a crash on a real fuzz target — the empirical baseline the user would be establishing.
- I found no work connecting the software-debloating literature (which knowingly removes vulnerabilities) to the optimization setting, though the measurement problem is the same and the debloating SoK's admission that removal of unknown reachable vulnerabilities is "undecidable" to evaluate is a useful concession to cite.
