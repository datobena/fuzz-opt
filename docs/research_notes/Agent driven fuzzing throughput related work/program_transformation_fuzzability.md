# Program Transformation for Fuzzability (and its inverse, Anti-Fuzzing)

Scope note for the report writer: every entry below is tagged with **[CRASH-PRESERVING]**, **[CRASH-CHANGING]**, or **[CRASH-PRESERVATION UNCLEAR]** because that is the user's key differentiator. "Crash-preserving" here means the transformed program is claimed/designed never to crash on inputs the original would not crash on, *and* never to lose crashes the original would produce. Where a paper only argues one direction, that is stated. Verification status is noted per entry; anything I could not confirm against a primary source is marked **UNVERIFIED**.

## Q1. Behavior-CHANGING transformations to ease fuzzing (T-Fuzz, TaintScope, checksum/magic bypass, program simplification) — how did they validate that real bugs were not lost, and what false-positive rates were reported?

### Takeaway
The canonical behavior-changing line (T-Fuzz, TaintScope) deliberately *breaks* the program — deleting or inverting sanity checks — and then pays for it with a post-processing oracle (symbolic execution to reproduce the crash on the untransformed program, or checksum repair of the crashing input). Both acknowledge the transformation both **adds** false crashes and can **lose** true bugs (T-Fuzz's own stated limitation is that removing a check can also remove the buggy path), and the reported cost is roughly ~2.8 alerts per true positive for T-Fuzz; none of them offer a guarantee of the "never crash less than the original" form the user's contract demands.

### Cited Findings

#### Recent (2024–2026)
- **FuzzSlice: Pruning False Positives in Static Analysis Warnings Through Function-Level Fuzzing** — Aniruddhan Murali, Noble Saji Mathews, Mahmoud Alfadel, Meiyappan Nagappan, Meng Xu; **ICSE 2024** (IEEE/ACM 46th ICSE, Lisbon, April 14–20 2024). Transformation: automatically generates *compilable function-level code slices* out of a real project and fuzzes the slice instead of the whole binary. **[CRASH-CHANGING]** — a slice executed with unconstrained inputs can crash where the whole program never could (the paper's premise is the inverse direction: "warnings without crashes during this fuzzing are probable false positives"). Validation/FP handling: evaluated on Juliet (all 864 ground-truth false positives detected) and on openssl/tmux/openssh-portable, identifying 33 of 53 developer-confirmed false positives; reported 62.26% false-positive reduction in real-world projects and 100% on the synthetic benchmark. — [arXiv abstract page](https://arxiv.org/abs/2402.01923); [ACM DL DOI 10.1145/3597503.3623321](https://dl.acm.org/doi/10.1145/3597503.3623321); [ICSE 2024 program entry](https://conf.researchr.org/details/icse-2024/icse-2024-research-track/39/FuzzSlice-Pruning-False-Positives-in-Static-Analysis-Warnings-through-Function-Level)
- **TOPr: Enhanced Static Code Pruning for Fast and Precise Directed Fuzzing** — arXiv:2309.09522 (Sept 2023; **UNVERIFIED** whether/where it was later formally published, and I did not verify the author list). Transformation: static, target-oriented *pruning* of code irrelevant to the directed-fuzzing target, using function-signature-matching heuristics instead of dynamic analysis. Reported: 222% and 73% higher test-case throughput vs. SieveFuzz and AFLGo respectively, 149%/9% more target-relevant coverage, 85%/8% faster bug triggering. **[CRASH-CHANGING]** — pruned executions are aborted when they leave the target-relevant region, so crashes outside the region are by construction not reported. — [arXiv abstract](https://arxiv.org/abs/2309.09522)

#### Seminal / older
- **T-Fuzz: Fuzzing by Program Transformation** — Hui Peng, Yan Shoshitaishvili, Mathias Payer; **39th IEEE Symposium on Security and Privacy (S&P/Oakland) 2018**, IEEE. Transformation: when the coverage-guided fuzzer plateaus, a lightweight dynamic-tracing technique detects the input checks the fuzzer's inputs fail ("non-critical checks") and **removes those checks from the target program**, producing a family of transformed programs that are then fuzzed. **[CRASH-CHANGING]** — the paper itself names the two consequences: "removal of checks causes over-approximation and false positives, and crashing inputs on transformed programs may not trigger bugs in original versions." FP handling: a symbolic-execution-based post-processing **Crash Analyzer** filters false positives and attempts to reproduce true bugs on the *original* program. Results: on the DARPA CGC dataset T-Fuzz finds bugs in **166 binaries vs. Driller 121 and AFL 105**; also evaluated on LAVA-M and four real programs (pngfix, tiffinfo, magick, pdftohtml), finding **3 previously unknown bugs**. — [ASU institutional publication record with full abstract](https://asu.elsevierpure.com/en/publications/t-fuzz-fuzzing-by-program-transformation/); [IEEE Xplore document 8418632](https://ieeexplore.ieee.org/document/8418632/); [author-hosted PDF](https://nebelwelt.net/files/18Oakland.pdf)
- T-Fuzz **false-positive cost**: on the CGC dataset T-Fuzz hands the Crash Analyzer **2.8 alerts per true-positive detection on average (median 2)**. — reported by a search summary quoting the paper text returned for [this query set](https://pdfs.semanticscholar.org/73f0/06514c0f349d55573a3c6e6de360dd56ab73.pdf); **flagged: I could not open the PDF to read this sentence directly — VERIFY before quoting in the report.**
- **TaintScope: A Checksum-Aware Directed Fuzzing Tool for Automatic Software Vulnerability Detection** — Tielei Wang, Tao Wei, Guofei Gu, Wei Zou; **IEEE Symposium on Security and Privacy (S&P) 2010**. Transformation: identifies checksum fields in inputs, locates checksum-based integrity checks via branch profiling, and **bypasses them by control-flow alteration** (i.e., patching the program so the check always passes), then fuzzes the modified program with taint-guided "hot byte" mutation. **[CRASH-CHANGING]** — crashes are found on a modified binary in which integrity checks no longer hold. Validation: the workflow requires repairing the crashing input (recomputing the checksum field) so the bug reproduces against the *unmodified* program; results: **30 previously unknown vulnerabilities** in Adobe Acrobat, Flash Player, Google Picasa, Microsoft Paint and others. — [dblp record (venue/year/authors)](https://dblp.org/rec/conf/sp/WangWGZ10.html); [IEEE Computer Society proceedings entry](https://www.computer.org/csdl/proceedings-article/sp/2010/05504701/12OmNvqEvNN). Extended journal version: **Checksum-Aware Fuzzing Combined with Dynamic Taint Analysis and Symbolic Execution**, ACM Transactions on Information and System Security (TISSEC) — [ACM DL DOI 10.1145/2019599.2019600](https://dl.acm.org/doi/10.1145/2019599.2019600). **Flagged: the precise checksum-repair algorithm and any reported false-positive rate could not be read (PDF unparseable) — VERIFY.**
- **CrFuzz: Fuzzing Multi-Purpose Programs through Input Validation** — ESEC/FSE 2020, ACM. Instruments/intercepts the target's *input-validation* phase so that inputs predicted to be rejected are cut short rather than fully executed. **[CRASH-PRESERVATION UNCLEAR]** — the mechanism deliberately truncates executions the original would have continued. — [ACM DL DOI 10.1145/3368089.3409769](https://dl.acm.org/doi/10.1145/3368089.3409769) (**authors UNVERIFIED — I only saw the DL title/venue listing**)
- **Production practice, not research, but it is the exact anti-pattern the user's contract bans:** the de-facto OSS-Fuzz/libFuzzer convention is to compile a *different* program for fuzzing. libFuzzer's own documentation defines `FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION` as the macro for "fuzzing-friendly" builds; AFL++ documents `#ifdef FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION` / `#ifdef __AFL_COMPILER` as the way to make checksum and validation code conditional; OpenSSL uses it to relax signature/CMP verification during fuzzing, and Rust's `ogg` crate uses `cfg!(fuzzing)` to skip checksum verification. **[CRASH-CHANGING by construction — the fuzzed binary is not the shipped binary.]** — [LLVM libFuzzer documentation](https://llvm.org/docs/LibFuzzer.html); [AFL++ "Fuzzing in Depth"](https://aflplus.plus/docs/fuzzing_in_depth/); [Fuchsia "Improving your fuzzer"](https://fuchsia.dev/fuchsia-src/development/testing/fuzzing/improve-a-fuzzer). The OpenSSL `crypto/cmp/cmp_vfy.c` and `ogg`-crate specifics came from a search summary of practitioner guidance pages (Trail of Bits "Overcoming Fuzzing Obstacles" handbook material) rather than a page I read end-to-end — **VERIFY the file-level claim if it is quoted.**

### Inferences
- The user's contract ("never crash less than the original; no fuzzing-only `#ifdef` gates") is precisely the *negation* of the two dominant prior paradigms: T-Fuzz/TaintScope break semantics and pay a triage tax afterwards; the OSS-Fuzz `FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION` convention breaks build-equivalence and pays a "fuzzed binary ≠ shipped binary" tax. Framing the novelty as "no triage tax and no build divergence" is well supported by this literature.
- T-Fuzz's ~2.8 alerts per true positive is the single most quotable number for the cost of behavior-changing transformation, and its explicitly stated failure mode (a removed check can remove the bug too) is the strongest evidence that prior work *does not* meet a "never crash less" guarantee.
- No work I found in this line offers an *a priori* (static/compile-time) argument of crash-equivalence; they are all *a posteriori* (filter after the fact).

### Gaps
- Exact per-dataset false-positive percentages for T-Fuzz (beyond alerts-per-true-positive) and any false-positive rate for TaintScope could not be extracted because PDF parsing failed in this environment.
- I found no paper that systematically measures *bugs lost* (false negatives) caused by check removal — T-Fuzz acknowledges the risk qualitatively but I found no quantified missed-bug study.

## Q2. Behavior-PRESERVING transformations: work that speeds up / improves a target while preserving semantics

### Takeaway
This is a small but real and growing line, and it is the closest prior art to the user's project: ClosureX (ASPLOS 2025) transforms *source code* with LLVM passes to make persistent fuzzing semantically correct (3.5× throughput), the CCS 2023 profile-guided work patches the target to reset state and replaces OS interactions with user-space abstractions, and Pogofuzz (FUZZING 2026) applies plain compiler PGO to the target — but every one of them is a *compiler/runtime* transformation, not an LLM agent editing project source, and only ClosureX makes correctness (no false crashes, no missed crashes) its explicit contribution.

### Cited Findings

#### Recent (2024–2026)
- **ClosureX: Compiler Support for Correct Persistent Fuzzing** — Rishi Ranjan, Ian Paterson, Matthew Hicks (Virginia Tech); **ASPLOS 2025** (30th ACM International Conference on Architectural Support for Programming Languages and Operating Systems, Volume 1), ACM, DOI 10.1145/3669940.3707281. Transformation: a set of **LLVM passes that transform the target's source** (the VT repository version of the paper is literally titled "CLOSUREX: Transforming Source Code for Correct Persistent Fuzzing") so that only *test-case-execution-specific* state is reset between iterations, integrated with AFL++. **[CRASH-PRESERVING — this is the paper's central claim]**: it explicitly frames naive persistent fuzzing as causing "semantically inconsistent program states … resulting in **missed crashes, false crashes**, and overall incorrectness", and positions ClosureX as giving "near-persistent performance with the correctness of heavyweight state restoration". Results on ten popular open-source fuzzing targets: **>3.5× higher test-case execution rate on average vs. AFL++**, bugs found **1.9× faster**, and **15 0-day bugs (4 CVEs)**. — [VT institutional record with abstract](https://vtechworks.lib.vt.edu/items/3439d99a-9205-40fa-bea0-91bad721bc66); [ACM DL entry](https://dl.acm.org/doi/10.1145/3669940.3707281); [author PDF](https://vtechworks.lib.vt.edu/bitstreams/820014dd-aaae-4bc6-8c4f-0f739a5fd78c/download)
- Companion VT dissertation: **"Towards Correct and Efficient Persistent Fuzzing: Reducing [state leakage]"** — defines state leakage as "remnants from one test case inadvertently influenc[ing] the outcome of subsequent ones, skewing results and potentially masking vulnerabilities", and notes persistent mode "eliminates all process creation, initialization, and tear-down costs — which are on-par with execution cost". **[CRASH-PRESERVING framing]** — [VT ETD PDF](https://vtechworks.lib.vt.edu/server/api/core/bitstreams/0001a39d-7a3b-49f0-8e4e-8f50adcc0282/content) (**exact title/author/year UNVERIFIED — PDF unparseable; the landing metadata was not retrieved**)
- **Pogofuzz: Profile-Guided Optimization for Fuzzing (Registered Report)** — Tobias Holl, Leon Weiß, Kevin Borgolte (Ruhr-Universität Bochum); **Proceedings of the 5th International Fuzzing Workshop (FUZZING 2026), February 2026** (co-located with NDSS). Transformation: uses the fuzzer's *known future inputs* (the corpus/queue) to drive **compiler profile-guided optimization of the target program**, fuzzer-agnostic and target-agnostic. **[CRASH-PRESERVING]** — PGO is a standard semantics-preserving compiler optimization; no program logic is removed. Reported preliminary result: **surpasses AFL++ by up to 4%**. Explicit motivating statement: "optimizing the performance of the target program, which the fuzzer executes billions of times, specifically for fuzzing has received little attention." — [RUB SoftSec publication page](https://softsec.rub.de/publications/fuzzing2026-pogofuzz/); [NDSS FUZZING 2026 PDF](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf)
- **SAND: Decoupling Sanitization from Fuzzing for Low Overhead** — arXiv:2402.16497 (**venue UNVERIFIED**; widely listed as ICSE 2025 but I did not confirm against ACM/IEEE). Runs a fast non-sanitized binary in the fuzzing loop and re-executes "interesting" inputs under sanitizers, "achieving near-native speeds while maintaining high bug-detection capabilities". **[CRASH-PRESERVING in intent]** — the bug oracle is preserved by re-execution rather than weakened. — [arXiv HTML](https://arxiv.org/html/2402.16497v2)

#### Seminal / older
- **Profile-guided System Optimizations for Accelerated Greybox Fuzzing** — Yunhang Zhang, Chengbin Pang, Stefan Nagy, Xun Chen, Jun Xu; **ACM CCS 2023** (Copenhagen), DOI 10.1145/3576915.3616636. Two profiling-informed techniques: (1) **patching the target program to reset critical execution states**, enabling "reliable and efficient persistent mode"; (2) **user-space abstractions that simulate OS functionality**, removing "complex but fuzzing-irrelevant" OS interactions from the hot path. Evaluated on 20 programs plus MAGMA, accelerating AFL and AFL++ to higher coverage and faster bug detection. **[CRASH-PRESERVING in intent]** — "reliable" persistent mode is the stated goal, i.e., avoiding the false/missed crashes of naive persistent looping; I could not read the PDF to confirm how strongly correctness is argued. — [ACM DL](https://dl.acm.org/doi/10.1145/3576915.3616636); [author-hosted PDF](https://futures.cs.utah.edu/papers/23CCS.pdf); [artifact](https://github.com/emptyiscolor/Profile-guided-Fuzzing)
- **laf-intel / "Circumventing Fuzzing Roadblocks with Compiler Transformations"** — originally a blog post by the pseudonymous "laf-intel", now shipped as AFL++'s LAF-Intel LLVM passes. Transformation: **splits wide comparisons (e.g. a 32-bit `== 0x12345678`) into cascaded byte-level comparisons**, plus split-switches, transform-comparison of string functions, and float splitting, so the fuzzer gets incremental coverage feedback. **[CRASH-PRESERVING]** — the transformation is semantics-preserving by construction (same predicate, different encoding); the only cost is code size/edge count. This is the strongest existing example of "semantics-preserving transformation purely to help the fuzzer". — [AFL++ LAF-Intel documentation](https://github.com/AFLplusplus/AFLplusplus/blob/stable/instrumentation/README.laf-intel.md); [original announcement thread](https://groups.google.com/g/afl-users/c/D_M683KaQkg)
- **Full-speed Fuzzing: Reducing Fuzzing Overhead through Coverage-guided Tracing** (UnTracer) — Stefan Nagy, Matthew Hicks; IEEE S&P 2019 (arXiv:1812.11875) (**venue/year from the arXiv listing and widespread citation; UNVERIFIED against IEEE Xplore in this session**). Transformation: self-modifying the *binary's* coverage instrumentation so that only coverage-increasing executions pay tracing cost. **[CRASH-PRESERVING]** — instrumentation-only; program logic untouched. — [arXiv PDF listing](https://arxiv.org/pdf/1812.11875)
- **Same Coverage, Less Bloat: Accelerating Binary-only Fuzzing with Coverage-preserving Coverage-guided Tracing** — ACM CCS 2021, DOI 10.1145/3460120.3484787 (arXiv:2209.03441). The title states the invariant: coverage-*preserving*. **[CRASH-PRESERVING]** — [ACM DL](https://dl.acm.org/doi/abs/10.1145/3460120.3484787)
- **Breaking Through Binaries: Compiler-quality Instrumentation for Better Binary-only Fuzzing** — USENIX Security 2021 (Nagy et al.). Introduces the phrase **"fuzzing-enhancing program transformations"** and reports compiler-quality overhead of 27% with **48–78% and 131–203% higher fuzzing throughput over AFL-Dyninst and AFL-QEMU** respectively. **[CRASH-PRESERVING]** (binary rewriting for instrumentation). — [USENIX PDF](https://www.usenix.org/system/files/sec21fall-nagy.pdf) (**author list UNVERIFIED — PDF unparseable in this session**)
- Sanitizer-cost reduction, a mixed sub-line where the crash-preservation question is explicit:
  - **SanRazor: Reducing Redundant Sanitizer Checks in C/C++ Programs** — Jiang Zhang, Shuai Wang, Manuel Rigger, Pinjia He, Zhendong Su; **USENIX OSDI 2021**. Removes sanitizer checks judged redundant via dynamic coverage + static data dependency. **[CRASH-CHANGING — measurably loses bugs]**: overhead drops from 73.8% to 28.0–62.0% (ASan) and 160.1% to 36.6–124.4% (UBSan), but on 38 CVEs across 10 programs the reduced checks "suffice to detect **at least 33 out of the 38** CVEs" — i.e., up to 5 detections lost. — [USENIX OSDI'21 page](https://www.usenix.org/conference/osdi21/presentation/zhang); [author PDF](https://pinjiahe.github.io/files/pdf/research/OSDI21.pdf)
  - **Debloating Address Sanitizer (ASan--)** — Yuchen Zhang, Chengbin Pang et al.; **USENIX Security 2022**. Reduces ASan overhead from 117.8% to 75.8% (−35.7%), increases fuzzing execution speed and branch coverage, deployed in Chromium and still detects community-found bugs. **[CRASH-PRESERVATION UNCLEAR — debloating removes checks deemed unnecessary; the paper argues empirically, not by proof]** — [USENIX PDF](https://www.usenix.org/system/files/sec22summer_zhang-yuchen.pdf)
  - **FuZZan: Efficient Sanitizer Metadata Design for Fuzzing** — Yuseok Jeon, WookHyun Han, Nathan Burow, Mathias Payer; **USENIX ATC 2020**. Swaps ASan's metadata structures for fuzzing-optimized ones; "new metadata structures have **the same bug detection capabilities** as the ones they replace". **[CRASH-PRESERVING — explicitly claimed]** — [USENIX ATC'20 page](https://www.usenix.org/conference/atc20/presentation/jeon)

### Inferences
- ClosureX is the single most important contrast/ally for the user's paper: same invariant (no false crashes, no missed crashes), same mechanism class (source-level transformation), same goal (throughput), but done by fixed compiler passes rather than an agent making project-specific semantic edits. The user should position their work as "what ClosureX does for process state, generalized to arbitrary project-specific hot-path rewrites, done by an LLM agent".
- Pogofuzz (FUZZING 2026) shows the community has only just started to treat "optimize the target program itself" as a research direction, and its ceiling with generic PGO is small (~4%) — which is a strong motivation for the user's agentic, algorithm-level rewrites.
- The sanitizer sub-line demonstrates that the field's existing standard for "did we lose bugs?" is *empirical CVE re-detection* (SanRazor's 33/38), not a preservation contract. A paper that can assert preservation structurally is genuinely differentiated.

### Gaps
- I found **no** prior work that states a formal or enforced contract of the form "the optimized binary must never crash less than the original" for general source-level performance edits. ClosureX is the nearest, but its scope is process-state reset.
- I could not verify Pogofuzz's evaluation details beyond the "up to 4%" figure (PDF unreadable), nor whether it discusses crash equivalence at all.

## Q3. Fuzz harness / driver transformation and optimization (harness quality, driver synthesis, fuzz blockers)

### Takeaway
There is a well-developed 2023–2026 literature on *drivers*: fuzz blockers show most OSS-Fuzz coverage plateaus come from deficiencies in the harness/target rather than the fuzzer, harness degradation over time turns out to be milder than expected, and a wave of LLM harness-synthesis agents (OGHarn, HarnessAgent, OSS-Fuzz-Gen) now write and repair drivers automatically — but all of it changes the *harness*, which the user's project explicitly treats as off-limits.

### Cited Findings

#### Recent (2024–2026)
- **An Empirical Study of Fuzz Harness Degradation** — Philipp Görz, Joschua Schilling, Nicolai Bissantz, Thorsten Holz; arXiv:2505.06177 (submitted 9 May 2025, revised 25 June 2026), published in **Proceedings of the ACM on Software Engineering**, DOI 10.1145/3808172 (**exact issue/conference track UNVERIFIED**). Studies OSS-Fuzz harnesses across **510 open-source C/C++ projects**. Key finding: "a consistent overall fuzzer coverage percentage for projects in OSS-Fuzz and a **surprising longevity of the bug-finding capability of harnesses even without explicit updates**, as long as they still build." — [arXiv abstract](https://arxiv.org/abs/2505.06177); [ACM DL](https://dl.acm.org/doi/10.1145/3808172)
- **No Harness, No Problem: Oracle-Guided Harnessing for Auto-Generating C API Fuzzing Harnesses** (OGHarn) — Gabriel Sherman, Stefan Nagy (University of Utah); **ICSE 2025** (IEEE/ACM 47th ICSE), DOI 10.1109/ICSE55347.2025.00239. Mutationally stitches candidate harnesses from API headers and validates them with **Correctness Oracles**: compilation, execution, and coverage change. Explicitly motivated by the observation that high-coverage auto-generated harnesses "frequently miss key API semantics — bringing with them invalid, unrealistic, or otherwise-impossible data and call sequences" (i.e., harness-induced false positives). Produces semantically-correct harnesses for real libraries "in as little as one hour". **[Harness-level; crash semantics of the library itself unchanged, but an invalid harness manufactures crashes the real API could not produce.]** — [ICSE 2025 program entry](https://conf.researchr.org/details/icse-2025/icse-2025-research-track/202/No-Harness-No-Problem-Oracle-guided-Harnessing-for-Auto-generating-C-API-Fuzzing-Ha); [ACM DL](https://dl.acm.org/doi/10.1109/ICSE55347.2025.00239); [author PDF](https://futures.cs.utah.edu/papers/25ICSE-b.pdf); [artifact](https://github.com/mayant15/OGHarn)
- **HarnessAgent: Scaling Automatic Fuzzing Harness Construction with Tool-Augmented LLM Pipelines** — arXiv:2512.03420 (**authors/venue UNVERIFIED**). Reports ~20% improvement in three-shot harness generation success over prior work: **87% success for C, 81% for C++**, and **>78% of generated harnesses produce measurable target-function coverage increases** in one-hour fuzzing runs. — [arXiv HTML](https://arxiv.org/html/2512.03420)
- **SoK: From Systematization to Best Practices in Fuzz Driver Generation** — Springer LNCS chapter, DOI 10.1007/978-981-96-9101-2_18 (**authors/venue-year UNVERIFIED — only the Springer listing was seen**). — [Springer link](https://link.springer.com/chapter/10.1007/978-981-96-9101-2_18)
- **Enhancing Fuzz Testing Efficiency through Automated Fuzz Target Generation** — *Programming and Computer Software* (Springer), DOI 10.1134/S0361768825700227 (2025) (**authors UNVERIFIED**). — [Springer link](https://link.springer.com/article/10.1134/S0361768825700227)
- Other 2026 harness-agent entries surfaced but not verified beyond title/arXiv id (list for completeness, all **UNVERIFIED**): *Coverage-Guided Multi-Agent Harness Generation for Java Library Fuzzing* (arXiv:2603.08616); *Quality-Assured Fuzz Harness Generation via the Four Principles Framework* (arXiv:2605.21824); *SyzHarness: Patch-Based Kernel Bug Reproduction with LLM-Synthesized Fuzzing Harnesses* (arXiv:2609.23889); *Thinking More, Harnessing Better: State Machine Guided Harness Automatic Generation* (arXiv:2607.07007).

#### Seminal / older (but directly on "fuzz blockers")
- **Beyond the Coverage Plateau: A Comprehensive Study of Fuzz Blockers (Registered Report)** — Wentao Gao, Van-Thuan Pham, Dongge Liu, Oliver Chang, Toby Murray, Benjamin I. P. Rubinstein; **Proceedings of the 2nd International Fuzzing Workshop (FUZZING '23)**, ACM, 2023, DOI 10.1145/3605157.3605177. Findings: most OSS-Fuzz projects sit at **~30% runtime coverage** despite millions of CPU-hours, so ~70% of each project is effectively unfuzzed; **many fuzz blockers stem from deficiencies in the existing targets rather than in the fuzzing engines**; and "the majority of top fuzz blockers are **not directly related to the program input**", motivating better automated fuzz-driver generation *and modification*. — [ACM DL](https://dl.acm.org/doi/abs/10.1145/3605157.3605177); [author-hosted PDF](https://thuanpv.github.io/publications/Fuzzing23_FuzzBlockers.pdf) (**abstract text above is from the ACM/author listings and search summaries; the PDF itself could not be parsed, and the per-category blocker statistics were not retrievable — VERIFY specific percentages**)
- **Fuzz target generation using LLMs (OSS-Fuzz / Fuzz Introspector)** — Google's own documented pipeline: Fuzz Introspector identifies under-fuzzed code, an LLM writes a new fuzz target, compilation failures are fed back for revision. Reported: valid targets generated for **160 C/C++ projects**, max line-coverage increase of **29%** over existing human-written targets; in one earlier cohort, 14 of 31 projects got a compiling new target that increased coverage. — [OSS-Fuzz documentation](https://google.github.io/oss-fuzz/research/llms/target_generation/)

### Inferences
- The fuzz-blocker result ("blockers are mostly not input-related" and "deficiencies in existing targets") is the best published justification for working on the *target/program* rather than the fuzzer — but note it was used by that community to justify editing **drivers**, whereas the user edits **project source under a preservation contract**. That is a clean, defensible gap.
- The harness-degradation result (bug-finding capability persists as long as the harness builds) weakens "harnesses rot" as a motivation and indirectly strengthens "the remaining lever is throughput/target efficiency".

### Gaps
- I could not retrieve the fuzz-blockers paper's taxonomy tables (how many blockers are checksum/magic-value vs. environment vs. driver-shape), which would be the most useful quantitative evidence for the user's framing.
- I found no study that measures how much of an OSS-Fuzz target's wall-clock time is spent in *avoidable* computation (the throughput analogue of the coverage-blocker study). This looks like a genuine hole the user's project fills.

## Q4. Anti-fuzzing as the inverse problem — what do anti-fuzzing papers say controls fuzzing speed?

### Takeaway
Anti-fuzzing papers are effectively a controlled experiment on which source-level properties govern fuzzing throughput and effectiveness: **latency on error/cold paths**, **the number and distribution of branches feeding the coverage map**, and **explicit vs. implicit data flow**. Fuzzification (USENIX Sec '19) shows that amplifying cold-path latency and polluting the coverage map cuts discovered paths by 70.3% and crashes by 93.0% while keeping normal-workload overhead within a user-specified budget — i.e., the same knobs the user's optimizer would turn in the opposite direction.

### Cited Findings

#### Recent (2024–2026)
- **CatchFuzz: Reliable active anti-fuzzing techniques against coverage-guided fuzzer** — *Computers & Security* (Elsevier), 2024 (**authors UNVERIFIED; volume/pages UNVERIFIED**). Detects the fuzzing environment via k-means clustering over shared-memory access patterns, then **directly manipulates code-coverage values to disorder the coverage feedback system**, explicitly *minimizing* the use of delay functions because "an attacker can easily detect significant fuzzing slowdown through the fuzzer's dashboard in real time". **[CRASH-CHANGING / feedback-changing by design]** — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0167404824002062)
- **Battling against Protocol Fuzzing: Protecting Networked Embedded Devices from Dynamic Fuzzers** — ACM TOSEM, DOI 10.1145/3641847, 2024 (**authors UNVERIFIED**). — [ACM DL](https://dl.acm.org/doi/10.1145/3641847)
- Reported effect of data-flow obfuscation as an anti-fuzzing measure: "inefficient mutations during fuzzing, taking **70% more time to expose crashes** than in unobfuscated code" (from a search summary of the anti-fuzzing literature — **source paper not pinned down; VERIFY or drop**).

#### Seminal / older
- **Fuzzification: Anti-Fuzzing Techniques** — Jinho Jung, Hong Hu, David Solodukhin, Daniel Pagan (Georgia Tech), Kyu Hyung Lee (University of Georgia), Taesoo Kim (Georgia Tech); **28th USENIX Security Symposium (USENIX Security '19)**, presented 16 Aug 2019. Three source/compiler-level transformations: **SpeedBump** (injects code into cold paths so that fuzzed executions are slowed "by hundreds of times" while normal workloads stay within a user-specified overhead), **BranchTrap** (fabricates branches to hide real paths and **pollute the coverage map**), **AntiHybrid** (converts explicit data flow to implicit data flow to defeat taint analysis and symbolic execution). Results: **−70.3% discovered paths, −93.0% identified crashes** on real-world binaries, **−67.5% bugs on LAVA-M**, all under user-specified overhead budgets for common workloads. **[CRASH-CHANGING — the explicit goal is to make the program crash less under fuzzing while behaving "normally" for users.]** — [USENIX presentation page with abstract](https://www.usenix.org/conference/usenixsecurity19/presentation/jung); [USENIX PDF](https://www.usenix.org/system/files/sec19fall_jung_prepub.pdf); [ACM DL proceedings entry](https://dl.acm.org/doi/10.5555/3361338.3361471)
- **AntiFuzz: Impeding Fuzzing Audits of Binary Executables** — Emre Güler, Cornelius Aschermann, Ali Abbasi, Thorsten Holz; **USENIX Security 2019**. Systematically enumerates the *fundamental assumptions* of fuzzers/symbolic execution and builds a countermeasure per assumption — including **injecting fake bugs/crashes**, **degrading error-path performance (inserting slow-down calls into code that handles malformed data)**, and defeating coverage feedback. Result: fuzzers reach in 24 hours only the coverage they would have reached in the first few minutes without AntiFuzz, at negligible overhead for normal use. **[CRASH-CHANGING — fake crashes are a deliberate false-positive injection.]** — [USENIX page](https://www.usenix.org/conference/usenixsecurity19/presentation/guler); [dblp record](https://dblp.org/rec/conf/uss/GulerAAH19.html); [USENIX PDF](https://www.usenix.org/system/files/sec19-guler.pdf)

### Inferences
- Read as a "which levers matter" study, the anti-fuzzing corpus says the controllable source-level throughput factors are: (1) **time spent on error/reject/cold paths** (the paths a fuzzer hits most often — SpeedBump/AntiFuzz both target exactly this); (2) **edge count and coverage-map density** (BranchTrap); (3) **explicitness of data flow** (AntiHybrid). For the user's optimizer, the productive inversions are: make the reject/error path as cheap as possible, avoid gratuitous edge explosion, keep comparisons explicit. This is a strong, citable argument for *which* source edits move throughput.
- AntiFuzz's "inject fake bugs" technique is the sharpest illustration of why "must never crash *more*" is not sufficient as a contract and why "never crash *less*" is the harder and more meaningful half — the user should note that anti-fuzzing attacks both directions.

### Gaps
- Neither Fuzzification nor AntiFuzz reports throughput (execs/sec) degradation broken down per technique in a form I could read (PDFs unparseable), so I cannot give an exact "cold-path latency → execs/sec" elasticity figure.
- I found no 2025–2026 anti-fuzzing paper that quantifies throughput levers on OSS-Fuzz-style in-process (libFuzzer) targets specifically; CatchFuzz and the TOSEM protocol work are the newest, and both target other settings.

## Q5. Removing/stubbing I/O, syscalls, randomness, time, or crypto from fuzz targets — and how it was argued safe

### Takeaway
Only one research entry squarely does this with a safety argument — the CCS 2023 profile-guided work replaces OS interactions with user-space abstractions on the grounds that they are "fuzzing-irrelevant" — while everything else in this space is either practitioner convention (`FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION`, `cfg!(fuzzing)`, `desock`-style preloads) that openly declares the build unsafe for production, or state-reset work (ClosureX) that restores rather than removes.

### Cited Findings
- **Recent / near-recent:** the CCS 2023 profile-guided optimization work introduces "**user-space abstractions to simulate OS functionality**, reducing expensive OS interactions", justified by the claim that the target's OS interactions involve "complex but **fuzzing-irrelevant** operations". **[CRASH-PRESERVATION ARGUED INFORMALLY — "fuzzing-irrelevant" is an efficiency argument, not a preservation proof]** — [ACM DL](https://dl.acm.org/doi/10.1145/3576915.3616636); [author PDF](https://futures.cs.utah.edu/papers/23CCS.pdf)
- **ClosureX (ASPLOS 2025)** handles the same class of problem the opposite way: rather than removing I/O, it resets test-case-specific state (including process state that persistent looping would otherwise leak), and treats correctness — no missed crashes, no false crashes — as the deliverable. — [VT record](https://vtechworks.lib.vt.edu/items/3439d99a-9205-40fa-bea0-91bad721bc66)
- **Practitioner convention (declared unsafe, not argued safe):** `FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION` is described as "the de-facto standard for making fuzzing practically possible, to disable certain fuzzing-unfriendly features (for example, **randomness**)" and to make "checksum and validation code conditional"; the macro name itself encodes that the resulting binary must not ship. — [LLVM libFuzzer docs](https://llvm.org/docs/LibFuzzer.html); [AFL++ Fuzzing in Depth](https://aflplus.plus/docs/fuzzing_in_depth/); [Fuchsia fuzzer-improvement guide](https://fuchsia.dev/fuchsia-src/development/testing/fuzzing/improve-a-fuzzer)
- **AFL++ persistent mode** states the preconditions that make in-process reuse legitimate: the target's "state can be **completely reset** so that multiple calls can be performed without resource leaks, and that earlier runs will have **no impact on future runs**." This is the closest thing to a written behavior-preservation contract in the tooling. — [AFL++ persistent mode README](https://github.com/AFLplusplus/AFLplusplus/blob/stable/instrumentation/README.persistent_mode.md)
- **Adjacent (environment replacement rather than stubbing):** *EmbedFuzz: High Speed Fuzzing Through Transplantation* (arXiv:2412.12746) transplants embedded firmware onto a host for speed (**venue/authors UNVERIFIED**) — [arXiv PDF](https://arxiv.org/pdf/2412.12746); *Designing New Operating Primitives to Improve Fuzzing Performance*, ACM CCS 2017, DOI 10.1145/3133956.3134046 — removes OS-level bottlenecks (fork/file) rather than editing the target — [ACM DL](https://dl.acm.org/doi/10.1145/3133956.3134046).
- Firmware-side evidence that *time* is a throughput sink: fuzzing throughput is reduced by "excessive use of time measurements in the firmware during which the firmware loops until an internal counter incremented on each SysTick interrupt reaches a certain value" (from the EmbedFuzz/embedded-fuzzing literature surfaced in search; **exact source paper not pinned — VERIFY**).

### Inferences
- There is essentially **no academic work that removes I/O/syscall/randomness/time from a fuzz target while arguing crash-equivalence**. The field's two positions are "replace the OS, it's irrelevant" (CCS'23, informal) and "gate it behind a fuzzing-only macro and admit the build is unsafe" (OSS-Fuzz convention). A contract-bound agent that does neither is a defensible novelty claim.
- The AFL++ persistent-mode preconditions give the user a ready-made, community-recognized vocabulary for stating their invariant ("no impact on future runs", "completely reset") that reviewers will already accept.

### Gaps
- I found no paper on stubbing **crypto** specifically (e.g., replacing a hash/AEAD with a cheap stand-in) with a safety argument; the only crypto-related practice found is OpenSSL's fuzzing-only relaxation of signature checks via the unsafe-for-production macro, which is the opposite of preservation.
- No quantified study of how much OSS-Fuzz target wall-clock goes to syscalls/I/O vs. compute.

## Q6. Work where an automated tool (not a human) proposed source edits to a fuzz target

### Takeaway
Automated source-edit proposals exist in three distinct flavors as of 2026 — LLM-generated *annotations* to the target (AIJon, 2026), LLM agents that generate/repair *harnesses* and build scripts (OSS-Fuzz-Gen, HarnessAgent, OGHarn), and LLM agents that generate *security patches* for OSS-Fuzz bugs (CodeRover-S) — but I found **none** whose objective is throughput/performance of the target under a behavior-preservation contract.

### Cited Findings

#### Recent (2024–2026)
- **AIJon: Automated Generation of Annotations for Fuzzing** — Jayakrishna Menon Vadayath, Hulin Wang, Moritz Schloegel, Jie Hu, Wil Gibbs, Tiffany Bao, Adam Doupé, Ruoyu "Fish" Wang, Yan Shoshitaishvili; **arXiv:2609.18457**, submitted 16 September 2026 (cs.CR) (**no peer-reviewed venue at time of writing**). Uses LLMs to automatically generate **IJON-style source annotations** in the target to steer the fuzzer, replacing the human expert. Evaluated on **Magma**: "LLMs can generate annotations that achieve comparable results to human generated" ones, but — notably — "**annotation-based fuzzing does not perform strictly better than AFL++**"; the paper attributes part of the effect to annotations changing "the energy distribution of the fuzzer". **[CRASH-PRESERVATION UNCLEAR — the abstract does not address whether annotations alter program semantics; IJON-style annotations can include forcing values and exposing state, which is behavior-changing in general.]** — [arXiv abstract page](https://arxiv.org/abs/2609.18457)
- **Fixing Security Vulnerabilities with AI in OSS-Fuzz** (CodeRover-S) — arXiv:2411.03346, later published as **"Fixing Security Vulnerabilities with Agentic AI in OSS-Fuzz"**, ICSE-SEIP 2026 (IEEE/ACM 48th ICSE: Software Engineering in Practice), DOI 10.1145/3786583.3786880 (**author list UNVERIFIED**). Adapts the AutoCodeRover agent to security patching: extracts vulnerability-relevant code by executing the exploit input and augments patch generation with static typing information; generates **plausible patches for 61%–72%** of historical OSS-Fuzz vulnerabilities, and was run on **45 unpatched vulnerabilities across 28 projects** disclosed Jan–Apr 2025. **[Changes program behavior intentionally — it is a bug fix, so the patched program crashes strictly *less*; exactly the opposite polarity to the user's contract.]** — [arXiv abstract](https://arxiv.org/abs/2411.03346); [ACM DOI](https://doi.org/10.1145/3786583.3786880)
- **OSS-Fuzz-Gen / OSS-Fuzz LLM pipeline** — Google. LLM writes new fuzz targets and iteratively repairs compilation failures; valid targets for **160 C/C++ projects**, up to **+29% line coverage** over human-written targets. There is also an OSS-Fuzz blog line on **agent-based build generation** for new project integrations. **[Harness/build-level, not project-source-level.]** — [OSS-Fuzz LLM documentation](https://google.github.io/oss-fuzz/research/llms/target_generation/); community forks/artifacts: [oss-fuzz-gen](https://github.com/xingyaner/oss-fuzz-gen), [fix_build_agent (agent for auto-fixing OSS-Fuzz build/fuzzing errors)](https://github.com/xingyaner/fix_build_agent)
- **HarnessAgent** (arXiv:2512.03420) and the 2026 harness-repair agents listed under Q3 — automated source edits confined to the harness. **[Harness-level.]**

#### Seminal / older
- **IJON: Exploring Deep State Spaces via Fuzzing** — Cornelius Aschermann, Sergej Schumilo, Ali Abbasi, Thorsten Holz; IEEE S&P 2020. The human-in-the-loop predecessor AIJon automates: an analyst inserts annotation macros into the target's source to expose internal state to the fuzzer's feedback. **[CRASH-PRESERVATION UNCLEAR / partly CRASH-CHANGING — annotations can force values and prune state.]** — **UNVERIFIED: my attempt to confirm venue/year/authors on dblp failed with a connection error in this session; treat the citation as needing a dblp/IEEE check before publication.**
- T-Fuzz (Q1) is the original "tool, not human, edits the target program" work, but it edits a binary/CFG rather than source and is explicitly behavior-changing. — [ASU record](https://asu.elsevierpure.com/en/publications/t-fuzz-fuzzing-by-program-transformation/)

### Inferences
- The 2024–2026 agentic-fuzzing literature has converged on three objectives — **write the harness**, **fix the build**, **fix the bug** — and has left **"make the target faster without changing what it does"** unoccupied. Combined with Pogofuzz's explicit statement that target-program optimization "has received little attention", this is the strongest available evidence for the user's novelty claim.
- AIJon's negative result (annotation-based fuzzing does not beat AFL++ strictly) is useful context: LLM-authored source modifications to fuzz targets have already been tried for *guidance* and underdelivered, which makes a throughput-focused, contract-bound formulation a more defensible target.

### Gaps
- I did not find any tool — LLM or otherwise — that proposes **performance** edits to an OSS-Fuzz project's own source and validates them against a crash-preservation oracle. If such work exists it is not surfacing under the obvious query phrasings; the closest neighbors are ClosureX (compiler passes, correctness-first) and Pogofuzz (PGO, no source edits).
- Author lists and formal venues for several 2026 arXiv entries (HarnessAgent, the harness-repair agents, CodeRover-S's published version) remain unverified.
