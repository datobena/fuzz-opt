# Agents Optimize Code, But Never Fuzz Targets

**Bottom line: the mechanism is not novel, the application is.** As of September 2026 there is a mature literature on LLM agents that profile code and accept only measured speedups — **PerfAgent** is architecturally the same loop, and it more than doubles expert-matching patch rates on GSO (**19.6% → 39.2%**) and SWE-fficiency-Lite (**26% → 74%**) ([arXiv:2607.19653](https://arxiv.org/abs/2607.19653)) — and a mature literature on making fuzzing faster, whose only entrant that optimizes the *target program itself* is **Pogofuzz**, a registered report that gets **up to 4% over AFL++ on four FuzzBench targets** with plain compiler PGO ([FUZZING 2026, DOI 10.14722/fuzzing.2026.23029](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf)). These two literatures have never been joined. Three independent lines of negative evidence — a 2026 agentic-fuzzing survey whose taxonomy has no target-optimization category, the AIxCC SoK covering seven maximally-resourced cyber reasoning systems, and an exhaustive keyword sweep — turn up **no published work in which an LLM or agent rewrites a fuzz target's application source to raise executions per second**. The strongest warrant for doing so is the CCS 2023 profiling study's finding that **"Of all the time, 84% is spent on Step 3 (executing the target program). In contrast, Step 1 and Step 2 account for 12% and 4% of the time"** ([Zhang et al., CCS 2023](https://futures.cs.utah.edu/papers/23CCS.pdf)) — the field has spent a decade optimizing the other 16%. The behavior-preservation contract is where the sharpest novelty lies: no published methodology argues *crash-behavior* preservation under a performance change, and the closest precedent, **"Don't Look UB"**, is a demonstration of the opposite — **17 sanitizer-eliding optimizations in Clang** that hid **20 real bugs** until disabled ([PLDI 2023, DOI 10.1145/3591257](https://pldi23.sigplan.org/details/pldi-2023-pldi/38/Don-t-Look-UB-Exposing-Sanitizer-Eliding-Compiler-Optimizations)).

## 1. Bottom line on novelty — what is and is not claimable

### Not claimable

**The agent architecture.** "LLM proposes an edit, a profiler says where, a measured gate says whether to keep it" is the dominant design pattern of 2025–2026. **PerfAgent** (Deng, Liu, Lipka, Ma, Chen, Kaler, Ganhotra; [arXiv:2607.19653](https://arxiv.org/abs/2607.19653), 22 Jul 2026) is a profiler-guided, verifier-in-the-loop workflow wrapped around an off-the-shelf coding agent with a curated profiler summary, selective test, and objective-driven controller; it explicitly argues for using **"profiler evidence rather than timing alone to decide what to optimize next."** **PRAGMA** builds the same loop on **Linux `perf` and Nsight Compute** for kernels, reporting **2.81× CPU / 2.30× GPU over Torch on KernelBench** ([arXiv:2511.06345](https://arxiv.org/abs/2511.06345)). Upstream of both, **FunSearch** ([Nature, Dec 2023](https://www.nature.com/articles/s41586-023-06924-6)) and **AlphaEvolve** ([DeepMind, May 2025](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)) established that the evaluator, not the LLM, is the source of truth. Do not claim the loop.

**"Optimize the target, not the fuzzer."** Pogofuzz claims this niche by name, and its related-work section states that prior work has "largely focused on improving or introducing fuzzer components" while optimizing target programs for fuzzing "has only received little attention" ([FUZZING 2026](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf)). The framing is taken.

**"Profile once, then patch the target."** Zhang, Pang, Nagy, Chen and Xu profiled each target for **five minutes** and then patched it — an LLVM pass plus GCC plugin for state reset, and a **~1,400 LoC user-space VFS** — at a top-four security venue ([CCS 2023, pp. 1257–1271, DOI 10.1145/3576915.3616636](https://dl.acm.org/doi/10.1145/3576915.3616636)). The methodology is precedented.

**"An LLM edits the target's source."** **Locus** (Jie Zhu et al., ICSE 2026, [DOI 10.1145/3744916.3773102](https://dl.acm.org/doi/10.1145/3744916.3773102); [arXiv:2508.21302](https://arxiv.org/pdf/2508.21302)) has an LLM agent synthesize compiler- and symbolic-execution-validated predicates that are compiled *into* the target. **AIJon** has an LLM write IJON-style annotations into target source ([arXiv:2609.18457](https://arxiv.org/abs/2609.18457)).

**ARVO as substrate.** CyberGym (ICLR 2026 Oral), CyberGym-E2E (ICLR 2026) and Meta's AutoPatchBench all sit on ARVO Docker images.

**Testing-based acceptance instead of proof.** Every entry in the LLM-optimization literature gates on tests or a scored evaluator; the field has no formal equivalence checking of LLM-produced C/C++ edits.

### Claimable

**The intersection is empty.** No published work — peer-reviewed or preprint — points an LLM at the execution speed of a fuzz target's own application code. This is supported by three independent kinds of evidence, not one search: the 2026 position paper **"Agentic Fuzzing: Opportunities and Challenges"** enumerates input generation, reasoning engine, pattern matching, harness engineering and seed scheduling, and contains **no throughput or target-speed category** ([arXiv:2605.10074](https://arxiv.org/html/2605.10074)); the **AIxCC SoK** finds no finalist CRS optimizing target execution speed beyond standard configuration, despite each team having **$85,000 Azure compute plus $50,000 LLM credits and ~143 hours of autonomous operation** ([arXiv:2602.07666](https://arxiv.org/html/2602.07666v2)); and a ~23-query sweep returned only harness, seed, mutator and patch work plus a disjoint code-performance literature.

**The crash-preservation contract.** There is **no published methodology for proving or systematically arguing that a performance change preserves crash behavior.** The property is not equivalence and not refinement — it is one-sided crash reflection, `crash(orig, x) ⟹ crash(opt, x)`. Classic compiler correctness proves the *converse* containment and is vacuous under undefined behavior: CompCert guarantees only that **"specifications that exclude 'going wrong' behaviors (safety-enforcing specifications) are preserved"** ([CompCert Complements](https://compcert.org/doc/html/compcert.driver.Complements.html)), which says nothing once the source program has UB — precisely the population a fuzz target explores. Stating the property in this direction, and enforcing it bidirectionally (also forbidding *new* crashes, which would inflate the experiment), is unclaimed territory.

**Single up-front profile over a frozen corpus of captured fuzzer mutations.** No work profiles on a fuzzing workload, ranks hotspots from a fixed replay corpus, or publishes a per-function breakdown of where OSS-Fuzz targets spend time under real fuzzer-generated inputs. The CCS 2023 study is stage-level (fuzzer / fork / target), not function-level within the target. A hotspot dataset across many ARVO targets would itself be a contribution.

**ARVO for time-to-bug, not for PoC-or-patch.** ARVO's canonical role is as a patching and reproduction corpus; CyberGym's own paper notes ARVO **"does not define any evaluation tasks or metrics, meaning it cannot serve as a benchmark on its own"** ([arXiv:2506.02548](https://arxiv.org/pdf/2506.02548)). No fuzzing-throughput or fuzzer-comparison paper uses ARVO. Time-to-bug on ARVO under a rewritten target is a new benchmark formulation, not just a new method.

**The algorithmic layer above the compiler.** Pogofuzz is the evidence, not the competition: if a compiler handed near-perfect fuzzing-workload profiles buys only single-digit percentages and regresses on two of four targets, the remaining headroom is above the compiler's abstraction level.

**An empirical baseline nobody has measured.** No study quantifies how often a *source-level* performance change makes a previously-crashing input stop crashing on a real fuzz target. Every reported failure rate for LLM edits is a functional-output failure rate, never a crash-behavior failure rate.

### The honest framing

Say plainly that the mechanism is borrowed and the contract, the domain and the endpoint are new. The defensible sentence is: *PerfAgent's loop, ClosureX's invariant, Pogofuzz's target, CCS'23's methodology, and ARVO's substrate, composed for the first time, with a crash-reflection contract that none of them states.*

## 2. Nearest prior art, closest first

**1. Pogofuzz: Profile-Guided Optimization for Fuzzing (Registered Report).** Tobias Holl, Leon Weiß, Kevin Borgolte (Ruhr University Bochum). *Proceedings of the 5th International Fuzzing Workshop (FUZZING 2026)*, co-located with NDSS, San Diego, 27 Feb 2026. DOI [10.14722/fuzzing.2026.23029](https://www.ndss-symposium.org/wp-content/uploads/fuzzing2026-29.pdf). Selects high-energy queue entries via the fuzzer's power schedule, generates a profile with a custom LLVM pass that scales PGO counter increments by test-case energy, then recompiles and hot-swaps the binary in situ on a one-hour timer. *How we differ:* the compiler chooses the transformation and re-profiles continuously; we make semantic source edits from one up-front profile and never recompile mid-campaign.

**2. Profile-Driven System Optimizations for Accelerated Greybox Fuzzing.** Yunhang Zhang, Chengbin Pang, Stefan Nagy, Xun Chen, Jun Xu. *CCS 2023*, pp. 1257–1271. DOI [10.1145/3576915.3616636](https://dl.acm.org/doi/10.1145/3576915.3616636). Five-minute profile, then two target patches: selective global-state save/restore, and a user-space VFS removing **~87% of syscalls** and **42% of kernel-space time**; combined **+142% (AFL) / +381% (AFL++)** execution speed, best per-target **17.5× on woff2**. *How we differ:* it patches state-reset machinery and the OS boundary, not the computation, and its validity check is fuzzing stability ≥95% rather than a crash contract.

**3. ClosureX: Compiler Support for Correct Persistent Fuzzing.** Rishi Ranjan, Ian Paterson, Matthew Hicks (Virginia Tech). *ASPLOS 2025*. DOI [10.1145/3669940.3707281](https://dl.acm.org/doi/10.1145/3669940.3707281). Five LLVM passes that undo only test-case-specific state; **>3.5× execution rate over AFL++**, bugs found **1.9× faster**, 15 zero-days and 4 CVEs, with "no missed crashes, no false crashes" as the explicit deliverable. *How we differ:* ClosureX is fixed compiler passes solving process-state leakage; we make project-specific algorithmic rewrites chosen by an agent.

**4. PerfAgent: Profiler-Guided Iterative Refinement for Repository-Level Code Optimization.** Ryan Deng, Yuanzhe Liu, Bastian Lipka, Yao Ma, Xuhao Chen, Tim Kaler, Jatin Ganhotra. [arXiv:2607.19653](https://arxiv.org/abs/2607.19653), 22 Jul 2026. **GSO 19.6% → 39.2%**, **SWE-fficiency-Lite 26% → 74%** expert-matching patches. *How we differ:* Python-fronted repositories with an expert-patch-match metric and a re-profiling loop; we target C/C++ under a single frozen profile with a security endpoint and a crash-reflection gate.

**5. Locus: Agentic Predicate Synthesis for Directed Fuzzing.** Jie Zhu et al. *ICSE 2026*. DOI [10.1145/3744916.3773102](https://dl.acm.org/doi/10.1145/3744916.3773102); [arXiv:2508.21302](https://arxiv.org/pdf/2508.21302). An LLM agent inserts validated predicates into the target; **70.3× average speedup for directed fuzzers (up to 214.2×)** and **~13× for coverage-guided fuzzers**. *How we differ:* Locus modifies the target for *signal* and its speedup is time-to-target-hit; we modify it for *speed* and our speedup is executions per second — reviewers will conflate these unless the distinction is drawn in the first sentence.

**6. "Don't Look UB: Exposing Sanitizer-Eliding Compiler Optimizations."** Raphael Isemann, Cristiano Giuffrida, Herbert Bos, Erik van der Kouwe, Klaus von Gleissenthall. *PLDI 2023*, DOI [10.1145/3591257](https://dl.acm.org/doi/10.1145/3591257). LookUB, a differential-testing framework, found **17 sanitizer-eliding optimizations in Clang**, and disabling them recovered **20 new bugs** in Linux Containers, libmpeg2, NTFS-3G and WINE that were previously hidden; the mitigation costs **4% overhead**. *How we differ:* this is our threat model's existence proof, not a competitor — and our threat model is strictly worse, since a compiler applies a fixed audited pass set while an agent applies unaudited source rewrites.

**7. "A Differential Fuzzing-Based Evaluation of Functional Equivalence in LLM-Generated Code Refactorings."** Simantika Bhattacharjee Dristi, Matthew B. Dwyer. [arXiv:2602.15761](https://arxiv.org/html/2602.15761v1), 17 Feb 2026. Across six LLMs, three datasets and two refactoring types, **19–35% of refactorings are functionally non-equivalent**, and **~21% of the non-equivalent ones pass the project's existing test suite**. *How we differ:* their oracle is functional output equivalence on generated inputs; ours is crash reflection on a replay corpus, and their 21% figure is our justification for not trusting unit tests as the semantics oracle.

**8. AIJon: Automated Generation of Annotations for Fuzzing.** Jayakrishna Menon Vadayath, Hulin Wang, Moritz Schloegel, Jie Hu, Wil Gibbs, Tiffany Bao, Adam Doupé, Ruoyu Wang, Yan Shoshitaishvili. [arXiv:2609.18457](https://arxiv.org/abs/2609.18457), 16 Sep 2026. LLM-generated IJON-style annotations reach human-comparable results on Magma, but **"annotation-based fuzzing does not perform strictly better than AFL++."** *How we differ:* annotations steer the fuzzer and can change semantics; our edits are contract-bound and change only cost. Its negative result is useful context — LLM source edits to fuzz targets have been tried for guidance and underdelivered.

**9. T-Fuzz: Fuzzing by Program Transformation.** Hui Peng, Yan Shoshitaishvili, Mathias Payer. *IEEE S&P 2018*, [IEEE Xplore 8418632](https://ieeexplore.ieee.org/document/8418632/). Removes non-critical input checks, finds bugs in **166 CGC binaries vs. Driller 121 and AFL 105**, and pays for it with a symbolic-execution Crash Analyzer at **~2.8 alerts per true positive**; the paper itself concedes that removing a check can remove the buggy path. *How we differ:* our contract is the exact negation — no triage tax, no build divergence, never crash less.

**10. TaintScope.** Tielei Wang, Tao Wei, Guofei Gu, Wei Zou. *IEEE S&P 2010* ([dblp](https://dblp.org/rec/conf/sp/WangWGZ10.html)); journal version ACM TISSEC, [DOI 10.1145/2019599.2019600](https://dl.acm.org/doi/10.1145/2019599.2019600). Patches out checksum checks, then repairs the crashing input to reproduce on the unmodified program; **30 previously unknown vulnerabilities**. *How we differ:* same polarity problem as T-Fuzz — crashes are found on a program that is not the shipped program.

**11. PIE / "Learning Performance-Improving Code Edits."** Alexander Shypula, Aman Madaan, Yimeng Zeng, Uri Alon, Jacob Gardner, Milad Hashemi, Graham Neubig, Parthasarathy Ranganathan, Osbert Bastani, Amir Yazdanbakhsh. *ICLR 2024 Spotlight*, [arXiv:2302.07867](https://arxiv.org/abs/2302.07867). The only major benchmark whose primary language is C++: **mean 6.86× with eight generations**, best generation **9.64×**, timed in **gem5** to remove wall-clock noise. *How we differ:* competitive-programming functions with bundled unit tests and simulated timing; we work at repository scale on real libraries with wall-clock replay.

**12. SeedSmith.** Junmin Zhu et al., [arXiv:2607.08949](https://arxiv.org/abs/2607.08949), Jul 2026. **11.51× (AFL++) to 14.66× (AFLGo) geometric-mean crash-time speedup on Magma** from better seeds alone. *How we differ:* orthogonal and in principle multiplicative — SeedSmith changes where the fuzzer goes, we change how fast each step costs. **An earlier search snippet claimed SeedSmith drew a random sample of 200 ARVO targets yielding 115 bugs across 26 projects; fetching the SeedSmith arXiv page did NOT confirm this selection protocol, so treat the claim as UNVERIFIED** — this matters because the benchmarks researcher separately concluded that **no fuzzing paper documents a seeded random sample of targets**.

**13. CyberGym.** [arXiv:2506.02548](https://arxiv.org/pdf/2506.02548), *ICLR 2026 Oral*. **1,507 vulnerabilities across 188 projects**, of which **1,368 come from ARVO** (cutoff 31 Jul 2024); task is PoC generation, oracle is a dual-binary check (crashes pre-patch, not post-patch). *How we differ:* their task is "produce a crashing input," ours is "make the campaign that finds it cheaper"; we inherit their three-stage QA filter chain as the selection precedent.

**14. AlphaEvolve.** Google DeepMind, May 2025. The strongest evidence that LLM-proposes / evaluator-gates yields deployed wins: **0.7% of Google's worldwide compute recovered**, **23% on a Gemini kernel → 1% of total training time**, **up to 32.5% on FlashAttention** ([DeepMind blog](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)). *How we differ:* Python and Verilog, internal Google systems, no behavior contract beyond the evaluator's own scoring.

## 3. The recent landscape, 2025–2026, by area

### Agentic performance optimization moved to repositories and away from C++

The field's center of gravity shifted in roughly eighteen months from *function-level, simulator-timed C++* to *repository-level, wall-clock-timed Python*. **GSO** offers **102 optimization tasks across 10 codebases** and reports that leading SWE-agents achieve **less than 5% success** ([arXiv:2505.23671](https://arxiv.org/abs/2505.23671); the repo is titled "[NeurIPS '25] GSO" but the arXiv page lists no venue). **SWE-Perf** has **140 PR-derived instances** and is an ICML 2026 poster ([arXiv:2507.12415](https://arxiv.org/abs/2507.12415)); its correctness oracle is unit tests only, with failure rates of **26.43% for Claude-4-Sonnet, 43.57% for GPT-4o, 57.14% for DeepSeek-V3** in the oracle/file-level setting. **SWE-fficiency** (**498 tasks across nine data-science/ML/HPC repositories**, [arXiv:2511.06090](https://arxiv.org/abs/2511.06090)) is the closest design analogue to a replay gate: it times a performance workload, verifies correctness with the repository's own tests, and **keeps the correctness and performance workloads separate**, explicitly rejecting unit-test runtime as a performance proxy. **FormulaCode** adds **957 bottlenecks with an average of 264.6 community workloads per task**, Python only ([arXiv:2603.16011](https://arxiv.org/abs/2603.16011)). **ECO** reports **up to 7.81×** from performance-aware prompting while "minimizing correctness loss" ([arXiv:2510.10517](https://arxiv.org/pdf/2510.10517)) — a weaker stance than a hard gate, and worth citing as the contrast.

C/C++ survives in this landscape mainly at the edges: **SuperCoder** superoptimizes **8,072 x86 assembly programs averaging 130 lines**, reaching **1.43× over `gcc -O3` with Claude-opus-4 at a 51.5% pass rate** and **1.46× at 95.0% correctness** after PPO/GRPO fine-tuning on a correctness-plus-speedup reward ([arXiv:2505.11480](https://arxiv.org/abs/2505.11480)); **KernelBench** defines **`fast_p`** — the fraction of kernels that are functionally correct *and* exceed a speedup threshold — which is the best-known published formalization of an accept/reject gate ([arXiv:2502.10517](https://arxiv.org/abs/2502.10517)); and **GI-Agent** runs LLM-driven genetic improvement on **MiniSAT (C++)** and SAT4J at the GI 2026 workshop co-located with ICSE 2026, DOI 10.1145/3786162.3793232, reporting only qualitative results ([ICSE 2026 program](https://conf.researchr.org/details/icse-2026/gi-2026-papers/1/GI-Agent-Search-Based-LLM-Agent-for-Code-Optimization-with-Genetic-Improvement)).

The one entry with a *structural* correctness guarantee is **Agentic Auto-Scheduling** (Merouani, Kara Bernou, Baghdadi, **PACT 2025**, [arXiv:2511.00592](https://arxiv.org/pdf/2511.00592)): a zero-shot LLM proposes loop transformations, the compiler returns polyhedral **legality** plus measured performance, and the result is **2.66× geometric mean on a single run, 3.54× best-of-5** on PolyBench. Cite it as the existence proof that stronger-than-testing correctness is possible, and concede that it is unavailable at library scale.

### Benchmark reliability became a first-class problem, and it is the argument for deterministic replay

The most directly usable 2026 result is **"Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents?"** by Zhi Chen, Zhensu Sun, Yuling Shi, David Lo and Lingxiao Jiang ([arXiv:2607.01211](https://arxiv.org/abs/2607.01211)). Replaying the benchmarks' own *reference* patches across different Google Cloud machine types, only **39/102 GSO**, **11/140 SWE-Perf** and **411/498 SWE-fficiency** tasks stayed valid. SWE-Perf is worst because "many reference patches produce close-to-zero runtime changes," making the measurement noise-dominated; official rankings disagreed on **9 of 28 pairwise comparisons**. This is the citation for why a fixed-corpus deterministic replay with a "must beat the previous best" rule is the right gate design: it mitigates both documented failure modes — cross-machine timing instability and near-zero-effect changes. A companion finding from the same year: with benchmark-provided test suites, **only 6.11%** of "performant" LLM implementations are significantly faster than canonical solutions ([arXiv:2607.07619](https://arxiv.org/abs/2607.07619)).

### Fuzzing throughput systems work continues, entirely outside the target's algorithms

The 2024–2026 crop keeps to the established taxonomy — eliminate process setup, eliminate tracing, reduce instrumentation density, improve binary rewriting, remove OS cost. **SAND** decouples sanitization from the fuzzing loop for **2.4× over ASan/UBSan configurations and 20× over MSan** on 20 programs (ICSE 2025 per IEEE Xplore; [arXiv:2402.16497](https://arxiv.org/abs/2402.16497)). **PeAR** brings persistent mode and shared-memory inputs to stripped binaries via Ddisasm/GTIRB, reporting **median 2.56×** for persistent mode and **median 4.07×** with shared memory across 20 FuzzBench benchmarks ([arXiv:2606.02126](https://arxiv.org/pdf/2606.02126), preprint). A Virginia Tech MS thesis (Sydney K. Earp, 2025) NOPs out `trace_pc_guard` call sites at runtime and reports **~30–40%** over fork-based throughput on the best targets. The honest comparison band for a general-purpose C/C++ user-space throughput technique is **1.3×–4×**; the four-orders-of-magnitude numbers (HSPFuzzer's **1062× vs AFLNet**, SAFIREFUZZ's **690×**) come from network, firmware and emulation settings with pathologically slow baselines and are not comparable.

### LLM agents colonized every part of the fuzzing loop except target speed

Harness generation is the crowded quadrant and the only one with an industrial deployment: **OSS-Fuzz-Gen** reports AI-generated targets improving coverage across **272 C/C++ projects, adding over 370,000 lines of newly covered code** and finding **26 new vulnerabilities** ([OSS-Fuzz blog](https://blog.oss-fuzz.com/posts/introducing-llm-based-harness-synthesis-for-unfuzzed-projects/)). Seed synthesis is second (**ELFuzz**, USENIX Security 2025, up to **+418.5% coverage**; SeedSmith's 11.5–14.7× crash-time geomean). Mutation and scheduling is where the field hit the throughput wall and named it: **"Inserting a single 100 ms LLM call per mutation drops throughput by three orders of magnitude"** ([FuzzPilot, arXiv:2605.26539](https://arxiv.org/pdf/2605.26539)). The community's universal response is to keep the LLM out of the hot loop — offline separation, stagnation-triggered invocation, or emitting a *program* that then runs at native speed. Nobody tried relaxing the constraint itself. Patching is the most peer-reviewed quadrant: **CodeRover-S** produces plausible patches for **61%–72% of historical OSS-Fuzz vulnerabilities** and **73.3% of unpatched ones** in deployment (Zhang, Wang, Berzin, Mitáš, Xie, Roychoudhury, *ICSE 2026 SEIP*, DOI [10.1145/3786583.3786880](https://doi.org/10.1145/3786583.3786880)). Benchmarks built on OSS-Fuzz/ARVO — CyberGym, CyberGym-E2E, SEC-bench, AutoPatchBench, FuzzingBrain-Bench — are uniformly "produce a crashing input and/or a patch." **None scores agents on throughput, exec/s, or coverage-per-CPU-hour.**

AIxCC is strong negative evidence at the systems-engineering level. Seven finalist CRSs ran **48 challenges (16 full-scan, 32 delta-scan) across 24 repositories with 63 vulnerabilities** over ~143 autonomous hours; final scores **Atlantis 392.8, Buttercup 219.4, RoboDuck 210.7** ([arXiv:2602.07666](https://arxiv.org/html/2602.07666v2)). Every team treated per-target execution speed as a fixed constraint to schedule around. **OSS-CRS**, the OpenSSF successor framework, has a pluggable component registry for fuzzers, seed generators, patchers and triagers — and **no "target optimizer" category**, which is itself a citable gap ([oss-crs.openssf.org](https://oss-crs.openssf.org/)).

### Semantics preservation: the 2026 consensus is that tests over-report correctness

Three independent 2026 measurements converge. Dristi and Dwyer's differential fuzzing finds **19–35% non-equivalent** LLM refactorings with **21% of those passing existing tests**. An Empirical Software Engineering study built **DataRef** (468 Java + 544 Python segments), generated **8,096 refactored segments**, and found **928 with behavioral inconsistencies and 180 outright failures** (DOI [10.1007/s10664-026-10911-6](https://link.springer.com/article/10.1007/s10664-026-10911-6)). Static preservation proxies range **81.8%–90.0%**, with assert/fail-call preservation passing in only **57.1%** of outputs ([arXiv:2510.03914](https://arxiv.org/pdf/2510.03914)). Meanwhile **EquiBench** shows LLMs are near-chance equivalence judges — best accuracies **63.8% and 76.2%** against a 50% baseline in the hardest categories, with models relying on "syntactic similarity rather than robust reasoning about program semantics" ([arXiv:2502.12466](https://arxiv.org/abs/2502.12466)) — which rules out any self-verification design. **SeGaBench** names the resulting stance well: LLMs are **"speculative semantic proposers"** requiring external validation ([arXiv:2608.03983](https://arxiv.org/abs/2608.03983)). SWE-Perf independently names the hazard the crash contract exists to prevent: **"functional pruning,"** where a model that can see the test modifies the code to retain only the functionality the test exercises.

Formal methods have not caught up. **DiffKemp** is the only equivalence checker demonstrated at whole-C-project scale — **the Linux kernel in minutes** ([ICST 2021](https://www.fit.vut.cz/person/vojnar/public/Publications/mv-icst21-diffkemp.pdf); TOSEM extension DOI [10.1145/3801958](https://dl.acm.org/doi/10.1145/3801958)) — but it works by near-syntactic LLVM-IR comparison plus a pattern library and will simply report "different" for an algorithmic rewrite. **Trivet** pairs an LLM with the Lean kernel and resolves **147 of 148 LLVM transformations (99.3%)** ([arXiv:2609.19583](https://arxiv.org/abs/2609.19583)) — still per-transformation. **Partial contracts** (Charalambous, Menezes, Sun, Cordeiro, [arXiv:2607.10291](https://arxiv.org/abs/2607.10291)) certifies **"safety-preserving conditional equivalence"** for C with LLM-inferred contracts, reports zero false proofs, and finds **nine EqBench pairs mislabeled as equivalent** — the closest formal phrase to the crash-reflection property, but not demonstrated at project scale.

### Evaluation methodology sharpened, and bug-based rankings turned out to be the noisy ones

**"In Bugs We Trust?"** (Madadi, Lee, Aschermann, Böhme, *PACMSE* 3(FSE), Article FSE084, Jul 2026, DOI [10.1145/3797112](https://doi.org/10.1145/3797112)) defines **concordance** as mean split-half reliability and finds that **coverage-based benchmarking is consistently strong while bug-based benchmarking is weak on FuzzBench and moderate on Magma**; the split-half reliability of ranking fuzzers by bugs found in 23 hours is weak. This is the strongest argument for pairing baseline and optimized arms on the *same* ARVO bug — same target, same seeds, same harness — which removes the between-target variance driving the low reliability. Two large-scale studies fill in context: **1.12 million OSS-Fuzz sessions across 878 projects** (IEEE TSE 2025, [arXiv:2510.16433](https://arxiv.org/pdf/2510.16433)) find **36% of projects detect a bug in the first session, 20% in the second**, dropping below 5% by the 26th and plateauing near a **2.19% median detection rate** — but the study never reports execs/sec, so it cannot be used to argue throughput drives discovery. And an **empirical study of fuzz harness degradation** across **510 OSS-Fuzz C/C++ projects** finds "a surprising longevity of the bug-finding capability of harnesses even without explicit updates, as long as they still build" (DOI [10.1145/3808172](https://dl.acm.org/doi/10.1145/3808172)) — which weakens "harnesses rot" as a motivation and indirectly strengthens "the remaining lever is target efficiency."

## 4. Older foundational work, by area

### Where fuzzing time actually goes

The single most important foundational number is the CCS 2023 profiling study over **12 OSS-Fuzz benchmark programs**, instrumenting AFL to time three stages per iteration across 24-hour campaigns on SSD and tmpfs: **"Of all the time, 84% is spent on Step 3 (executing the target program). In contrast, Step 1 and Step 2 account for 12% and 4% of the time."** Supporting numbers from the same study: tmpfs instead of SSD reduces iteration time by only **~2%**; in persistent mode **syscalls are 16.72% of execution time** with **file operations >85% of syscalls**; page faults under fork-server mode run **55% higher** than under snapshot mode. The complementary statistic comes from **UnTracer**: coverage-increasing test cases are on average **0.0062%** of all test cases for AFL-Clang, **0.0257%** for AFL-QEMU, **0.00653%** for Driller-AFL — so more than 99.99% of tracing work is discarded ([arXiv:1812.11875](https://arxiv.org/pdf/1812.11875)).

### Reducing per-execution overhead (2017–2023)

Xu, Kashyap, Min and Kim showed AFL **"slows down by 24× because of file system contention and the scalability of fork()"** at 120 cores and introduced three new OS primitives, speeding AFL by **6.1×–28.9×** and libFuzzer by **1.1×–735.7×** (*CCS 2017*, DOI [10.1145/3133956.3134046](https://dl.acm.org/doi/10.1145/3133956.3134046)). **kAFL** put Intel PT coverage overhead **below 5%** (*USENIX Security 2017*). **INSTRIM** instruments ~20% of basic blocks (*NDSS BAR 2018*). **UnTracer / Full-speed Fuzzing** (Nagy & Hicks, *IEEE S&P 2019*) got average relative execution time to **1.003 (0.3% overhead)** versus AFL-Clang 1.36, AFL-Dyninst 6.18 and AFL-QEMU 7.12. **PTrix** (*AsiaCCS 2019*, DOI [10.1145/3321705.3329828](https://dl.acm.org/doi/10.1145/3321705.3329828)) reached **17,000 execs/sec** by parallelizing PT-trace decoding. **Agamotto** (*USENIX Security 2020*) added **+66.6%** for Syzkaller on USB drivers. **Zeror** (*ASE 2020*, DOI [10.1145/3324884.3416572](https://dl.acm.org/doi/10.1145/3324884.3416572)) improved AFL and MOPT speed by **159.80%** with self-modifying tracing. **FuZZan** (*USENIX ATC 2020*) redesigned sanitizer metadata while claiming "the same bug detection capabilities." **ZAFL** (*USENIX Security 2021*) delivered **+48–78% over AFL-Dyninst and +159–203% over AFL-QEMU**. **HeXcite** (*CCS 2021*) extended coverage-guided tracing to edges and hit counts for **11.4× over QEMU, 24.1× over Dyninst, 2.8× over AFL-Clang**, with time-to-exposure **52.4% faster than UnTracer**. **Nyx** (*USENIX Security 2021*) and **Nyx-Net** (*EuroSys 2022*, DOI [10.1145/3492321.3519591](https://dl.acm.org/doi/pdf/10.1145/3492321.3519591), **up to 300×**) built the snapshot line; **SnapFuzz** (Andronidis & Cadar, [arXiv:2201.04048](https://arxiv.org/pdf/2201.04048)) reached **mean 24.6×** on network applications. **ASan--** (*USENIX Security 2022*) cut ASan overhead from 117.8% to 75.8%, raising AFL speed **>40%** and branch coverage **5%**, and was deployed in Chromium for four weeks. **LibAFL** (Fioraldi, Maier, Zhang, Balzarotti, *CCS 2022*, DOI [10.1145/3548606.3560602](https://dl.acm.org/doi/10.1145/3548606.3560602)) made near-linear multicore scaling a framework property via LLMP.

Two entries in this line trade bug detection for speed and are the cautionary citations. **SanRazor** (*OSDI 2021*) removes "redundant" sanitizer checks, cutting ASan overhead from 73.8% to 28.0–62.0% — but on 38 CVEs across 10 programs the reduced checks detect **at least 33 of 38**, meaning up to five detections lost. **Fuzzification** (*USENIX Security 2019*) and **AntiFuzz** (*USENIX Security 2019*) are the deliberate inverse: SpeedBump, BranchTrap and AntiHybrid cut **discovered paths by 70.3%, identified crashes by 93.0%, and LAVA-M bugs by 67.5%** while staying inside a user-specified overhead budget. Read as a controlled experiment, anti-fuzzing tells you exactly which source-level knobs govern throughput — **cold/error-path latency, edge count and coverage-map density, and explicitness of data flow** — and the productive inversions follow directly.

### Program transformation for fuzzability

Behavior-changing: **TaintScope** (S&P 2010), **T-Fuzz** (S&P 2018), **CrFuzz** (*ESEC/FSE 2020*, DOI [10.1145/3368089.3409769](https://dl.acm.org/doi/10.1145/3368089.3409769)), **FuzzSlice** (*ICSE 2024*, DOI [10.1145/3597503.3623321](https://dl.acm.org/doi/10.1145/3597503.3623321)), **TOPr** ([arXiv:2309.09522](https://arxiv.org/abs/2309.09522), **+222% / +73% throughput** by pruning target-irrelevant code). Behavior-preserving: **laf-intel**'s comparison splitting, shipped in AFL++, is the cleanest example of a semantics-preserving transformation done purely to help the fuzzer. Human-in-the-loop source annotation: **IJON** (S&P 2020), whose automation AIJon attempts. And the production anti-pattern the contract bans: `FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION`, the de-facto OSS-Fuzz convention for compiling a *different* program for fuzzing — the macro name itself encodes that the binary must not ship ([LLVM libFuzzer docs](https://llvm.org/docs/LibFuzzer.html)). **AFL++'s persistent-mode README** supplies ready-made, community-recognized vocabulary for the invariant: state "can be completely reset so that multiple calls can be performed without resource leaks," and "earlier runs will have no impact on future runs."

Motivation for working on the target rather than the fuzzer comes from the fuzz-blockers study (Gao, Pham, Liu, Chang, Murray, Rubinstein, *FUZZING '23*, DOI [10.1145/3605157.3605177](https://dl.acm.org/doi/abs/10.1145/3605157.3605177)): most OSS-Fuzz projects sit at **~30% runtime coverage** despite millions of CPU-hours, **many fuzz blockers stem from deficiencies in the targets rather than the engines**, and "the majority of top fuzz blockers are not directly related to the program input." Practitioner guidance corroborates that the problem is real and manually solved today: Chromium's efficient-fuzzing guide sets a hard bar — **"aim for at least 1,000 exec/s from your fuzz target locally before submitting it to the Chromium repository"** — and google/fuzzing tells authors to **"profile fuzz targets and eliminate any obvious hot spots,"** noting that **under 10 exec/s means "you are probably doing something wrong."**

### Equivalence, verification, and optimizations that hide bugs

Translation validation begins with **Pnueli, Siegel and Singerman** (*TACAS 1998*, LNCS 1384, pp. 151–166) and **Necula** (*PLDI 2000*). **Alive** (Lopes, Menendez, Nagarakatte, Regehr, *PLDI 2015*) proves peephole optimizations with Z3; **Alive2** (Lopes, Lee, Hur, Liu, Regehr, *PLDI 2021*, pp. 65–79, DOI [10.1145/3453483.3454030](https://dl.acm.org/doi/10.1145/3453483.3454030)) is explicitly bounded — it "limits resource consumption by, for example, unrolling loops up to some bound, which means there are circumstances in which it misses bugs" — and found **47 new bugs (28 fixed)** in LLVM's unit test suite. **CompCert** (Leroy, *CACM 2009*) is the verified-compilation alternative, with the UB caveat noted above. **Robust Safety Preservation** (*CCS 2018*, [arXiv:1802.00588](https://arxiv.org/pdf/1802.00588)) is the secure-compilation criterion built for UB-induced compromise, and **trace-relating compiler correctness** ([arXiv:1907.05320](https://arxiv.org/pdf/1907.05320)) is the machinery for relating source crashes to target crashes. **EMI** (Le, Afshari, Su, *PLDI 2014*, DOI [10.1145/2594291.2594334](https://dl.acm.org/doi/10.1145/2594291.2594334)) yielded **147 confirmed unique bug reports for GCC and LLVM**, and is differential testing's compiler-scale ancestor. **EqBench** (Badihi et al., *MSR 2021 Data Showcase*) supplies **147 equivalent and 125 non-equivalent** C/Java pairs.

The "optimization hides a bug" precedent has three independent legs. **STACK** (Wang, Zeldovich, Kaashoek, Solar-Lezama, *SOSP 2013*) defines *optimization-unstable code* — "code that is unexpectedly discarded by compiler optimizations due to undefined behavior" — with the consequence that "security checks can be discarded, weaknesses are amplified, and system behavior becomes unpredictable," and found **161 new bugs, confirmed and fixed**. **"Dead Store Elimination (Still) Considered Harmful"** (Yang, Johannesmeyer, Olesen, Lerner, Levchenko, *USENIX Security 2017*) found **4 of 11** security projects using flawed scrubbing and 4 more using it inconsistently. And **"Don't Look UB"** (PLDI 2023) closes the loop for sanitizer-instrumented fuzzing specifically. Wang et al.'s "unstable code" is the right term of art at the source level: a source change that alters whether UB is present changes what the compiler is licensed to delete, so a source "optimization" can mask a crash with no change to compiler flags.

The closest published discipline for the acceptance gate is **program reduction**. C-Reduce's designers state the epistemic stance exactly: **"Only a small proportion of C-Reduce's transformation passes is intended to be semantics-preserving in the sense that a compiler's optimization passes must be, since the goal is only to preserve enough semantics to probabilistically avoid breaking whatever property makes a test case interesting"** ([IEEE Software Blog](http://blog.ieeesoftware.org/2019/07/design-and-evolution-of-c-reduce-part-1.html)). Quote it. It is the honest description of what an empirical crash-preservation gate can and cannot promise.

One more foundational instrument worth adopting: **Magma**'s distinction between a bug being **reached** and **triggered** (Hazimeh, Herrera, Payer; **118 bugs, 11 CWEs, 7 targets, 200,000 CPU-hours**; [arXiv:2009.01120](https://arxiv.org/abs/2009.01120)). Magma verifies every forward-ported bug remains reachable and triggerable before admitting it, on the stated grounds that "without verification, forward-porting may inject bugs which cannot be triggered." An optimization that preserves reachability but destroys triggerability — memoizing past a faulting call, or making an out-of-bounds read land inside a now-larger buffer — is exactly the failure mode to rule out, and Magma's canary model is an implementable design for a check stronger than "the binary crashed."

Finally, two cautionary foundational results for the fold taxonomy: **Hort, Vidziunas and Moonen** surveyed 28 publications containing 94 transformations, implemented 39, and found **23 of 39 transformations change code semantics** (*Mutation 2025 @ ICST 2025*, [arXiv:2503.23448](https://arxiv.org/abs/2503.23448)) — so no category should be claimed behavior-preserving by construction; and the debloating SoK concedes that removal of previously-unknown reachable vulnerabilities is "generally not possible to evaluate because [it is] undecidable."

## 6. Open gaps this project can claim

**The joined literatures.** LLM code-performance optimization measures speedup of arbitrary code; fuzzing-throughput systems work measures exec/s. Both measure the right thing and no paper connects them.

**Crash-behavior preservation as a stated methodology.** No published technique proves, argues, or systematically tests that a performance change preserves crashing. Searches over "crash equivalence," "crash-preserving transformation," "bug-preserving optimization" and "vulnerability-preserving refactoring" return file-system crash consistency or generic functional equivalence. The bidirectional formulation — a finite approximation of bisimulation restricted to the crash observable — is unstated in the literature.

**The empirical base rate.** No study measures how often a source-level optimization removes a crash on a real fuzz target. Every reported LLM edit failure rate is functional.

**Mutation testing applied to a build rather than a test suite.** Treat the original project as the fault-carrying program, the known crash artifacts (or Magma-style canaries) as the fault set, and define the optimized build's *bug-detection-preservation score* as the fraction of the original's ground-truth faults still triggered. No paper does this composition.

**A per-function hotspot profile of OSS-Fuzz targets under real fuzzer inputs.** The CCS 2023 study is stage-level. Nobody has quantified what fraction of a fuzz target's per-execution work is input-invariant setup — re-parsing static tables, re-initializing constant structures, re-reading configuration — which is precisely what a profiling pass across many ARVO targets would produce, and which the "84% is in the target" figure makes the most valuable missing dataset in the area.

**A controlled measurement of build-flag effects on OSS-Fuzz throughput.** No published measurement of `-O2` vs `-O3` vs `-march=native` vs LTO vs PGO vs BOLT on OSS-Fuzz target execs/sec as a controlled experiment. Pogofuzz is the only PGO data point and covers four targets. Pogofuzz itself names BOLT and Propeller as the obvious next step and does not evaluate them.

**ARVO as a fuzzing-efficiency benchmark.** No fuzzer-comparison or throughput paper uses ARVO; no benchmark anywhere scores agents on throughput, exec/s, or coverage-per-CPU-hour; OSS-CRS's component registry has no target-optimizer category.

**A run-to-run distribution for an optimization agent.** No paper reports mean ± sd or a histogram of end-to-end achieved speedup across repeated identical agent invocations. Best-of-5 versus single-run (Agentic Auto-Scheduling: **3.54× vs 2.66×**, a ~33% relative gap purely from resampling) is the closest published figure. Filling this is cheap and citable.

**Survival analysis with right-censoring for time-to-bug.** Neither Klees nor Schloegel discusses censoring, and both assume a scalar per-trial outcome. Mann-Whitney on censored times is biased. A log-rank or stratified survival model is *stronger* than either canon prescribes and should be presented as a methodological contribution, not a deviation.

**Two caveats to pre-empt.** First, the calibration: industrial LLM-optimization results cluster in the single-digit-to-~30% band on already-tuned code (**AlphaEvolve 0.7% fleet compute, 23% Gemini kernel; MPCO up to 19.06%**), while benchmark results reach 2–9×. Fuzzing-throughput gains in the tens of percent are consistent with the industrial regime and should be framed that way so they are not read as underwhelming. Second, the corpus-choice weakness: replaying only saved crash artifacts tests the contract on inputs chosen before the optimization existed, and Dristi & Dwyer's 21%-evade-tests result is the direct warning. The published strengthening is continuous differential execution — feeding the live fuzzer's mutated inputs to both binaries and comparing the crash observable — plus Magma-style canaries so that "reached but not triggered" is distinguishable from "not reached."

## Conclusion

The literature is arranged such that every individual ingredient of this project has a strong, recent, citable precedent, and the composition has none. That is the rare configuration in which a related-work section becomes an asset instead of a defensive exercise: each nearest neighbor supplies a component and simultaneously certifies that the component is sound. PerfAgent legitimizes the profiler-guided agent loop; Chen et al.'s cross-machine audit legitimizes deterministic replay; SWE-fficiency legitimizes separating the correctness workload from the timing workload; ClosureX legitimizes the no-missed-crash invariant as a publishable deliverable; CCS'23 legitimizes profile-then-patch as a security-venue methodology; Böhme and Falk's second law legitimizes time-to-bug as the endpoint a throughput paper should measure; CyberGym legitimizes filtering ARVO. The work to be done in the paper is to make the seams visible and argue that the composition is more than the parts — principally by showing that the algorithmic layer above the compiler contains headroom that Pogofuzz's ~4% ceiling implies but cannot reach.

The sharpest remaining risk is not novelty but the contract's epistemic status, and the literature is unusually clear about how to talk about it. The crash-reflection property is not equivalence, standard compiler correctness proves the wrong direction and goes vacuous exactly where fuzz targets live, and nothing at library scale can prove the right one. What remains is the program-reduction discipline — define the interestingness predicate and re-check it empirically on every candidate — which C-Reduce's designers described honestly two decades into its use as preserving "enough semantics to probabilistically avoid breaking whatever property makes a test case interesting." Adopting that phrasing, adding Magma's reached-versus-triggered distinction so a masked bug is distinguishable from an unreached one, and reporting the base rate at which source-level optimizations silently destroy crashes would turn the weakest part of the design into the part that is hardest for a reviewer to dismiss — because nobody has measured it before.
