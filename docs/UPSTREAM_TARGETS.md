## What this is

A third manifest kind, `upstream`, beside `arvo` and `fuzzbench`: OSS-Fuzz projects at today's
upstream HEAD, built and fuzzed the way OSS-Fuzz does, so a crash a campaign finds is a claim
about upstream code (a candidate 0-day). Design: `docs/superpowers/specs/2026-11-05-upstream-targets-design.md`.
Measurement rules, in one paragraph: each project's OSS-Fuzz directory is vendored verbatim from
OSS-Fuzz commit `f3af0cb37c1a5fbc8be71f4ad13135b6f9de9acd` into `prework/upstream/<project>/ossfuzz/`
and built with OSS-Fuzz's own `compile` (`FUZZING_ENGINE=afl`, the CFLAGS `compile` composes,
existing OSS-Fuzz harnesses only, every sanitizer `project.yaml` lists, rebuilds under
`--network none`); trials reproduce `run_fuzzer`'s afl branch (`afl-fuzz -m none [-c ...] [-x ...]
-i <corpus> -o <out> -- /out/<target>` in `/out`, the eight `run_fuzzer` `AFL_*` env keys, base-runner's
`ASAN_OPTIONS`/`MSAN_OPTIONS`/`UBSAN_OPTIONS` composed with the target's `.options` sections) plus
only pipeline mechanics (`-V`, `-s`, `AFL_AUTORESUME=1`, core pin, the mutation-capture shim on the
optimized arm only). Two user-decided deviations from `run_fuzzer`, applied to both arms and
recorded in every launch record: `-t 1000` instead of `-t 5000+`, and `detect_leaks=0` appended
last to `ASAN_OPTIONS`. The gate, preflight smoke, profiler and trials all run under the same
sanitizer options. No PoC; bug survival is `no-poc`.

## The fix policy

Binding text: `.superpowers/sdd/2026-11-05-upstream-targets/fix-policy.md`. A fix may change how the
build environment is obtained, never what is compiled or how it is instrumented. Editable:
`prework/upstream/<P>/Dockerfile`, build scripts in `ossfuzz/`, and `meta.json["deviations"]` only.

Allowed (each recorded as a deviation):

- A1 pin a dependency version/commit or install a missing package.
- A2 move a compile-time fetch into the Dockerfile so `compile` runs with `--network none`, same versions.
- A3 work around toolchain drift with the pinned base image, the one-line change OSS-Fuzz maintainers would make.
- A4 fix a moved clone URL or branch.
- A5 (R1) exclude from a build loop a harness that does not compile at HEAD; harness file untouched; meas. true.
- A6 (R2) rebase an OSS-Fuzz-shipped patch whose hunks change only in context/offsets.
- A7 skip a seed/dictionary-only fetch that cannot be moved; meas. true.

Forbidden:

- F1 changing sanitizer, optimization or instrumentation flags.
- F2 modifying harness code, fuzz entrypoints or the build glue's semantics (beyond A5/A6).
- F3 patching the target's or a dependency's source.
- F4 (R3) pinning the main repository below HEAD (dependencies may be pinned under A1).
- F5 changing the base image/digest or `SANITIZER`/`FUZZING_ENGINE`/`FUZZING_LANGUAGE`.

Cap: three fix rounds per project; if only F1-F5 would work, the project is dropped with the reason.
Each change was made by a fixer agent and approved by a separate auditor before the controller committed it.

## Known limitations

- Slow-calibration smoke timeouts: a harness with thousands of seeds and a slow target exceeds the preflight smoke's `secs + 300` s timeout (420 s at `--smoke-secs 120`) during AFL's seed calibration, so it gets NOT READY although the profiler ran the corpus fine. In the snapshot: hpn-ssh `kex_fuzz` (6731 seeds), address 970003 and undefined 970011. A campaign just calibrates longer; these entries are usable.
- The verdict wording does not name that cause. It reads `NOT READY: exception: TimeoutExpired: Command '[...]' timed out after 420 seconds` and embeds the whole `docker run` command in the table cell.
- Preflight wall time per pass-1 entry was 323-1585 s (`pass1_driver.log`), dominated by the baseline compile; pass 1 shared one build cpuset, so later entries include queueing.
- samba: engine not OSS-Fuzz's (R10); UBSan build fails (recoverable `__ubsan_handle_*_overflow` unresolved linking a host tool through afl-clang-fast++), not pursued since the fix would be F1/F5.
- xmlsec: hardening flags off (R7); afl-cc in the pinned image treats `-fcf-protection` as a CFI request and emits LTO bitcode, breaking the libtool link.
- rnp: Botan 3.13.0, not 3.4.0 (R8); 3.4.0 cannot build rnp HEAD's module list.
- openvpn: `fuzz_list` not built or fuzzed (R1/A5).
- `report`'s `_preflights` loads every `*.json` under `--preflight-dir` recursively and keys on any `local_id` field, so a stray JSON carrying a `local_id` there would be taken for a verdict.
- Trial mechanics that differ from OSS-Fuzz's base-runner: trials run in the project's builder image (not base-runner) as the host uid:gid with `OUT` set; the host does not set `vm.mmap_rnd_bits=28` as base-runner's `run_fuzzer` does, so ASLR entropy under ASan differs; the preflight smoke runs `afl-fuzz` without the `PATH=/out:$PATH` prefix the trial launch uses.
- samba's five-core preflight builds succeed (7,640 execs/s smoke on `fuzz_cli_credentials_parse_string`); one earlier builder run on a single core failed after 39 min with exit 123 (xargs) while other heavy builds ran, and could not be reproduced by hand on one core (2,188 s, 203 executables). Treat single-core samba builds with suspicion; give its builder several cores.
- Optimized trials' `metadata.json` has `toolchain: null` (pre-existing for all kinds); the upstream pins travel on the baseline trials, and triage falls back to them.
- Harnesses whose hot code is generated at build time (samba's `fuzz_ndr_*` NDR marshalling, generated under `bin/default/` inside the container's copy of the tree) fail the preflight's profile stage with `source-root mismatch: no function of the build maps to the editable tree`. That is the right verdict for the optimizer: nothing it could edit survives a rebuild. Such harnesses can still be fuzzed baseline-only.
